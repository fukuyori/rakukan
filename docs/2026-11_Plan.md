## 1. 候補

### 1.1 辞書の版の整理

辞書（`rakukan.dict`）を決める項目は、`rakukan.dict.build.json` の `mozc_rev`・`mozc_source`（元データ）、`dict_schema`（中身の作り方）、`format_version`（ファイルの構造。辞書のヘッダーにもある）。`builder_version` は辞書を作ったときの rakukan の版で、参考の記録として残す。engine が `format_version` の不一致で辞書を拒む処理は、安全装置として残す。

| 作業 | 重要度 | 内容 |
|---|---|---|
| 決まりの直し | 中 | [version-update-checklist.md](version-update-checklist.md) の 4.1 と `cost_band::DICT_SCHEMA` のコメントを、「ビルダーの出力が変わる変更（入れる語・除く語、cost、候補の順、記号・絵文字の扱い、渡す引数、ファイルの構造）をしたら `dict_schema` を上げる」にする。今は cost 帯の意味を変えたときだけで、ほかの変更では辞書が作り直されず、中身の古い辞書が配布物に入りうる |
| 作り直しの判定と表示 | 低 | `scripts/build-installer.ps1` の作り直しの判定に `format_version` を足す（ファイルの構造を変えて `dict_schema` を上げ忘れると、古い構造の辞書が配布物に入り、engine が拒む）。同梱する辞書の 4 項目をビルドのときに表示する |
| ホストのログ | 低 | engine が辞書を読み込むとき、`build.json` の `mozc_rev`・`dict_schema`・`format_version` をホストのログに書く |
| 設定アプリ | 低 | 「バージョン情報」に、辞書の mozc の版・作り方の版・構造の版を出す |

engine DLL と設定アプリを変えるので、確かめるにはビルドと導入（再起動）が要る。4 つをまとめて実装し、1 回の導入で確かめる。

## 2. 10 月の計画から移したもの（ログが無かったため、11 月に行う）

中身は [October_Plan.md](October_Plan.md) の 7 節。

- **#57 の運用確認**: #57（変換が遅く返ったときの誤った再起動）は、PR #59 で詰まりの監視をホストへ移し、実行番号で数える形にした（0.11.9 から）。クローズの条件は、運用ログで誤った再起動が無いことを確かめること。ホストのログで、詰まりによる自己終了（理由・実行番号・経過時間・試行回数）の件数を数え、正当な長い変換で発動していないかを確かめる。暫定の閾値（30 秒）の見直しも、このログで行う（#57 の 2026-09-18 のコメント）。問題が無ければクローズする。
- **#50 の照合と段 2**: 10 月の計画で入れる段 1（原因を確かめるログ）のビルドで運用し、ログがたまってから、`skipped save for dead dm` の理由と `unknown dm` の DM が台帳に載らない理由を照合する。その結果で段 2 の直し方を決める（2026-10-24 の #50 のコメントの「直し方の案」の段 2: 同じスレッドなら遅れて処理する側での列挙のやり直し、別のスレッドなら #86 と合わせる、生きている DM を死んだと扱う例があればその経路を直す）。段 2 の後に、ブラウザのタブの切り替えや複数回の Activate があるアプリで、`unknown dm`・`skipped save` の出方とモードの復元を確かめる。

- **1 か月分のログで再計測**: 0.11.9 の後の指標（`live_continuation_guard fallback` など月単位の目標）を、ビルドごとに分けて数える。期間には 0.11.9・0.12.0・0.13.0・0.13.1 のビルドが入る。ビルドはログの 1 行目のヘッダー（0.13.1 からは `rakukan log header: … build=…`）で決まる。
- **#83 の計測と小さな改善**（engine の中だけで閉じ、RPC・ABI を変えない）: Space の変換のビームサーチの所要時間を、読みの長さ別・CPU / Vulkan / CUDA 別にログで取る。続けて、上位 k 件の選択を全体のソートから部分選択に変える（新旧の候補が一致することを試験で確かめる）。KV キャッシュの再利用（フェーズ 5）は、この結果を見て判断する。
