## 2. フェーズ 1（段 A）: #71

**作業**（Issue #71 の「直し方の方向」に、レビューの指摘を加えた）

1. `OnCompositionTerminated`（`crates/rakukan-tsf/src/tsf/factory.rs`）で、終了した composition を照合してから処理する。照合に使う DM・Owner は `composition_set(None)` の前に控える。**照合は RPC の状態だけでなく、候補ウィンドウ・タイマー・セッションの後始末より前に行う**（今はそれらも無条件に消している）。今フォーカスのある別の composition（同じ DM に新しい Owner ができた場合を含む）を、RPC の状態も表示も壊さない。
2. `close()` も終了した composition を指定して行う（今は「今の DM」の状態を消す。`rpc_composition.rs`）。
3. 終了の処理では所有権を取り直さない。Restore は送らず、手元の既存の `Expect` に対する Change（`ResetAll`）だけを試みる。呼び出し元の `foreground` を引き継がない。
4. 失敗しても手元の状態は必ず閉じる。エンジンが無い場合も `close()` する。
5. 未解決要求の照合と放棄は、台帳のロックの中で行い、対象を終了した composition の Owner・世代・要求番号に限る（今の `abandon()` は無条件の `take()`。`crates/rakukan-engine-rpc/src/client.rs`）。BgReclaim の応答が失われた後の `ResetAll` の扱い（送る順序・放棄する対象・最後の手元の状態）を決める。
6. `Deactivate` の `bg_reclaim()`（`close()` の後で送られずに戻る）も同じ方針で扱う。
7. 確かめられるように記録を足す（今のホストのログは要求の内容を記録せず、時間がかかったときだけ `rpc: {label} took …ms` を残す）。

   | 場所 | 残す情報 |
   |---|---|
   | ホストの `dispatch_change`（照合の経路） | `ResetAll`、要求番号、期待と現在の Owner・世代、適用・保存した応答の再送・拒否・エラーの区別。**保存した成功応答の再送を「今回消した」と記録しない** |
   | ホストの `apply_change` の `ResetAll` | 消す前と後の `committed` が空か（必要なら長さ。本文は残さない）。既存 ABI の `committed_text()` で取れる（文字列をコピーするので、診断を有効にしたときだけ） |

   毎回の記録は DEBUG。ホストは `RUST_LOG`、engine DLL は `RAKUKAN_LOG` で有効にする。試験のときは全件を記録する。

**完了条件**

- 単体の試験: 正常な終了、状態が無いとき、ホストを入れ替えた直後、別の Owner、別の DM / 同じ DM の遅れた通知、BG 変換中、BgReclaim / ResetAll の応答の消失。**消す前に `committed` が空でない状態を作って**確かめる（`reset_preedit` は文脈を残し `reset_all` は消す、の対照も）。
- 期待値: 対象と既存の `Expect` が有効で通信できる場合、`ResetAll` が適用され `committed` が空になる。それ以外では、拒否・未送信・結果不明を区別して記録し、対象の手元の状態を閉じる。終了処理は Restore を送らず、別の composition（RPC の状態・候補・タイマー・セッション）と、別の composition の未解決要求を変えない。
- 実機: フォーカスの移動で WARN（`timer or irreversible request cannot acquire ownership`）が出ない。作業 7 の記録で上の期待値どおりであることを確かめる。普段の入力・変換が変わらない。

## 3. フェーズ 2（段 B）: #69 / #70

**B-1 定義**（設計の前に決める。#69 の本文のとおり）

1. 1 つのキーをどこまで処理したか（受け取った・再送用に保持した・ホストに適用した・アプリへの文書操作を始めた）
2. 読み・未確定ローマ字・表示の文字列を分けて持つこと
3. アプリへの確定がどこまで済んだか（確定前・確定済みで新しい composition が未開始・新しい composition を開始済み）

**B-2 設計**: 設計書（`docs/Input_Pipeline_Plan.md`、仮）を書き、Codex CLI のレビューを受ける。下の論点と、各論点の「設計で決めること」をチェックリストとして扱う。
