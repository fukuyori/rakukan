# 候補の並びの見直し（mozc に合わせる・ユーザー辞書の優先度・珍しい記号）

作成: 2026-11-21

状態: 計画（未実装）。決めたことは 9 章。

関係する Issue: #79（珍しい記号の降格）、#29（ユーザー辞書の優先度）、#40 の 2（候補の末尾の ひらがな・カタカナ。`4c95242` で実装済み）、#84（単漢字）、#13・#37（Step 12 で決めた今の順）。

## 1. 目的

Space の変換とライブ変換の候補の並び（engine の `merge_candidates_for_reading`）を、できるだけ mozc の並べ方に合わせる。あわせて、次の 2 つを同じ並べ方の中で扱う。

- #79: ヒエログリフや珍しい仮名が、普通の読みの変換で上位（4 番目前後）に出る。
- #29: ユーザー辞書に大量に登録すると、一度も学習していない語でもシステム辞書の語より前に出て、普通の変換が荒れる。

## 2. mozc の並べ方（調べた事実）

手元のクローン（`1527a4cd1`、2026-11-20）のコードで確かめた。mozc は、辞書の順番で並べるのではなく、コストで競わせてから、並べ替えの処理（rewriter）で動かす。rewriter は `rewriter/rewriter.cc` の順に動く。

| 段 | 処理 | 内容 |
|---|---|---|
| 1 | 辞書を引く（`dictionary/dictionary_impl.cc`） | システム辞書・値の辞書・ユーザー辞書を同じように引く。引いた順では並べない。ユーザー辞書の抑制単語に当たる語は、ここで落とす |
| 1 | ユーザー辞書の語のコスト（`dictionary/user_dictionary.cc`・`user_pos.cc`） | 品詞ごとの固定の値（`user_pos.def`。品詞なし・名詞 2500、固有名詞・人名 1500、組織・地名 2000、短縮よみ 200 など）に、語の数 N による罰則 `500 × ln(N+1)` を足す（10 語で +1,198、1,000 語で +3,454）。品詞なしの短い読みには、さらに足す |
| 2 | 変換（ラティス） | システム辞書とユーザー辞書の語を、同じラティスの上でコストで競わせる。先頭の候補はコストで決まる |
| 3 | `UserDictionaryRewriter` | ユーザー辞書の候補を、先頭のすぐ後ろ（2 番目）へ寄せる。先頭は動かさない。ユーザー辞書の候補どうしの並びは保つ |
| 4 | `SingleKanjiRewriter` | 単漢字を末尾に足す |
| 5 | `EmojiRewriter` | 絵文字を 6 番目に差し込む |
| 6 | `SymbolRewriter` | 記号を 3 番目の後ろに差し込む（`symbol_rewriter_candidate_position` の既定 3）。そこから続く「1 文字の漢字・ひらがなだけ・カタカナだけ」の候補は飛ばす。前に出すのは 15 個まで（`symbol_rewriter_promotion_size` の既定 15）。残りが 5 個未満なら全部前に出す。説明の列が同じ記号は途中で切らない。残りは最後へ |
| 6 | 珍しい記号（`IsRareSymbolForDemotion`） | 当たったら前に出すのをやめ、それ以降の記号はすべて最後へ。ヒエログリフは読みが「ひえろぐりふ」のときだけ下げない。変体仮名・濁点付き仮名・鼻濁音・アイヌ語カナは、読みにかかわらず下げる |
| 7 | `UserSegmentHistoryRewriter` | 学習した候補を先頭へ動かす（点数が最上位に近いものを最大 5 個） |

## 3. 今の rakukan の並べ方

`crates/rakukan-engine/src/lib.rs` の `merge_candidate_lists` と `place_symbol_candidates`。

- 固定の順に積む: 学習履歴 → ユーザー辞書 → システム辞書 → LLM（Step 12、#13・#37）。システム辞書は LLM の枠を残して積む。
- 学習していない読みでは、ユーザー辞書の語が必ず先頭になる。
- 記号は上位 3 件の後ろに 15 個まで。残りの記号は末尾、絵文字はさらにその後ろ。記号の種類による区別は無い。
- 最後に、ひらがな・カタカナを足す（#40 の 2）。
- システム辞書（`rakukan.dict`）は、語ごとに表記とコスト（mozc の辞書の値）だけを持つ。品詞の番号は持たない。ユーザー辞書（`user_dict.toml`）は読みと表記だけを持つ。

コストの例（今の辞書の実測。小さいほど優先）:

| 読み | 候補とコスト |
|---|---|
| きょう | 今日 121、共 2505、きょう 3449、強 3688、鏡 3758 |
| かいぎ | 会議 3638、懐疑 5508、回議 7016 |
| もりの | 森野 4857、守野 6297、モリノ 7291 |

## 4. 新しい並べ方

### 4.1 全体の順

```
学習履歴
→ コストで決まった先頭（システム辞書と normal の語を比べる。同じならシステム辞書）
→ ユーザー辞書（normal）を 2 番目へ寄せる
→ システム辞書の残り
→ ユーザー辞書（low）
→ LLM の候補
   （このうえで、記号を 3 番目の後ろに、絵文字を 6 番目に差し込む）
→ 記号の残り
→ ひらがな・カタカナ
→ 珍しい記号
```

記号と絵文字の位置は、学習履歴を除いた並びの上で決める。学習した候補は、最後に先頭へ動かす（mozc で学習の rewriter が最後に動くのと同じ）。

### 4.2 ユーザー辞書の語のコスト

- `normal` の語のコストは、mozc の品詞なしの式 `2500 + 500 × ln(N+1)` にする。
- N は `normal` の語の数だけを数える。`low` の語は先頭を争わないので、数に入れない。
- システム辞書の語とコストで比べ、いちばん安い語を先頭にする。同じコストならシステム辞書を先にする。
- 品詞による値の違い（固有名詞 1500 など）は入れない。`user_dict.toml` は品詞を持たないため。

### 4.3 ユーザー辞書の語を 2 番目へ寄せる

- `normal` の語は、4.2 で先頭になっていなければ、2 番目から続けて置く（mozc の `UserDictionaryRewriter`）。ユーザー辞書の語どうしの並びは、4.2 のコストの順（同じなら登録の順）。
- 基本の並びが空（システム辞書に無い読み）なら、ユーザー辞書の語が先頭になる。

### 4.4 ユーザー辞書の優先度（#29）

`user_dict.toml` の項目に `priority` を足す。値は `normal`（既定）と `low`。

```toml
[[entries]]
reading  = "やまだ"
surfaces = ["山田太郎"]
priority = "low"      # 省略したときは "normal"
```

- 優先度は項目（1 つの読みと、その表記の並び）ごとに付ける。
- 既定の `normal` はファイルに書き出さない。今の `user_dict.toml` は変えなくても動く。
- `low` の語は、先頭を争わず、2 番目へも寄せない。システム辞書の残りの後ろ、LLM の候補の前に置く（#29 の提案の順のまま）。
- `low` の語も、一度選べば学習で先頭に来る。使わなくなれば学習の点数が下がって元の位置に戻る。
- 設定アプリは、ユーザー辞書の編集の画面に優先度の選択（「通常」「低」）を足し、一覧に「低」の印を出す。今の設定アプリは保存のときに各項目を読みと表記だけで作り直す（`MainWindow.xaml.cs`）ので、保存のときにも優先度を残すようにする。

#29 の環境（約 2,200 件）での見込み（計算した値）:

- 全部 `normal` のまま: N=2,200 でコスト 6,348。普通の語より先頭になることはほぼ無いが、2 番目へは寄せられるので、読みが衝突する一般語は 3 番目以降に下がる。
- 人名を `low` にする: 人名はシステム辞書の語の後ろに回り、一般語の並びは変わらない。残りの `normal` の語（たとえば 10 件）は N=10 の 3,698 で比べられる。

### 4.5 絵文字

6 番目に差し込む（mozc の `EmojiRewriter`）。そのあと記号を 3 番目の後ろに差し込むので、並びは「上位 3 件 → 記号 → 普通の候補 → 絵文字」になる。

### 4.6 記号

- 3 番目の後ろに差し込む。そこから続く「1 文字の漢字・ひらがなだけ・カタカナだけ」の候補は飛ばして、その後ろに入れる。
- 前に出すのは 15 個まで。残りが 5 個未満なら全部前に出す。
- 「説明の列が同じ記号は途中で切らない」は入れない。rakukan の辞書は記号の説明の列を持たないため。
- 残りの記号は、ひらがな・カタカナの前に置く。

### 4.7 珍しい記号（#79）

記号の候補の並び（`symbol.tsv` の行順）の中で、珍しい記号に当たったら、そこで前に出すのをやめ、それ以降の記号はすべて最後へ回す。

文字のコードで判定する（辞書の作り直しは要らない）。

| 文字のコード | 当たるもの |
|---|---|
| U+13000〜1343F | ヒエログリフ |
| U+31F0〜31FF | アイヌ語カナ（小書きのカタカナ） |
| U+3099・U+309A | 結合用の濁点・半濁点（`か゚`・`く゚` などの組み合わせ） |
| U+30F7〜30FA | `ヷ ヸ ヹ ヺ` |

- 辞書を作るときの mozc の版（`cbbb6e1bd`）の `symbol.tsv`（2,106 行）で、説明の列が「ヒエログリフ」「濁点付き仮名」「鼻濁音」「アイヌ語カナ」の 120 行すべてに一致し、ほかの記号には当たらないことを確かめた（2026-11-21）。変体仮名は辞書を作るときに除いている（`has_unrenderable_kana`）。
- 例外は mozc と同じく、読みが「ひえろぐりふ」のときのヒエログリフだけ。ほかは、どの読みでも下げる。
- 下げた記号は、ひらがな・カタカナより後ろ（いちばん最後）に置く。

### 4.8 学習

今と同じく、学習した候補を先頭に置く。mozc の「最上位に近いものを最大 5 個」の決まりは入れない（学習の点数の付け方が mozc と違うため）。

### 4.9 ひらがな・カタカナ（#40 の 2）

今と同じ規則で足す（読みと違う候補が 1 件も無いときは足さない、すでにあるものは足さない）。置き場所は、記号の残りの後ろ、珍しい記号の前。

## 5. 例

システム辞書のコストは実測。ユーザー辞書の語は `normal`、N=10（3,698）として計算した。

| 読み | 登録した語 | 新しい並び（先頭から） | 今の並び |
|---|---|---|---|
| もりの | 杜野 | 杜野（3,698 < 森野 4,857）、森野、守野 … | 杜野、森野 … |
| かいぎ | 解義 | 会議（3,638 < 3,698）、解義、懐疑 … | 解義、会議 … |
| きょう | 京 | 今日、京、共、きょう … | 京、今日 … |
| ぞう | ― | 像、増、ぞう、蔵、象 … 𓃰（最後） | 像、増、ぞう、𓃰、蔵、象 … |

## 6. 利用者から見て変わること

- 登録した語は、普通の語より安ければ先頭、そうでなければ 2 番目になる。学習すれば先頭になる（今と同じ）。ライブ変換のプレビュー（読みと違う最初の候補）も、この並びに従う。
- `low` にした語は、システム辞書の語の後ろに回る。
- 絵文字が 6 番目あたりに出てくる。
- ヒエログリフ・珍しい仮名は、いちばん最後に回る。「ひえろぐりふ」と読めばヒエログリフは前に出る。
- 記号は、上位の候補のあとに続く 1 文字の漢字・かなだけの候補の後ろに入る。

## 7. 作業

engine の中の変更（段 1・段 2）と、ユーザー辞書の形式・設定アプリの変更（段 3）に分ける。辞書の作り直し、RPC・ABI の変更は無い。3 つの段をまとめて実装し、1 回の導入で試験する。

| 段 | 内容 | 主な場所 |
|---|---|---|
| 1 | 記号・絵文字・珍しい記号の並べ方（4.5〜4.7）と、学習・ひらがな・カタカナの位置（4.8・4.9） | `crates/rakukan-engine/src/lib.rs`（`place_symbol_candidates` と、その前後） |
| 2 | ユーザー辞書の語のコストと、2 番目へ寄せる処理（4.2・4.3）。システム辞書をコスト付きで引く口を足す（今の `lookup_dict` は表記だけを返す） | `crates/rakukan-dict/src/store.rs`、`crates/rakukan-engine/src/lib.rs`（`merge_candidate_lists`） |
| 3 | `priority` の読み書き（4.4）。engine は `low` の語を別に引く。設定アプリは優先度を選べるようにし、保存のときに残す | `crates/rakukan-dict/src/user_dict.rs`・`store.rs`、`apps/rakukan-settings-winui/`（`MainWindow.xaml`・`MainWindow.xaml.cs`・`SettingsStore.cs`） |

#29 にある nick さんの参考実装（`feat/user-dict-priority`）は、Step 12 より前の順を前提にしているので、そのままは使わない。`priority` を TOML に既定値で書き出さない形は合わせる。

## 8. 試験

単体の試験:

- 4.2: コストで先頭が決まる（ユーザー辞書が安い・高い・同じ）。N に `low` を数えない。
- 4.3: 2 番目へ寄せる。ユーザー辞書の語が複数あるときの並び。基本の並びが空のとき。
- 4.4: `low` の語の位置（システム辞書の後ろ、LLM の前）。`priority` を省略した項目は `normal`。`normal` は書き出さない。
- 4.5: 絵文字の位置（候補が 6 件未満のときを含む）。
- 4.6: 記号の飛ばし（1 文字の漢字・ひらがなだけ・カタカナだけ）。15 個まで。残りが 5 個未満なら全部。
- 4.7: 判定の関数（各範囲の文字、`ヷ`、普通の記号は当たらない）。珍しい記号に当たってからの記号は最後へ。「ひえろぐりふ」ではヒエログリフを下げない。
- 4.8・4.9: 学習した候補が先頭。ひらがな・カタカナが珍しい記号の前。
- 今の試験（`learned_surface_outranks_user_dict_entry` など）を、新しい並びに合わせる。

実機の試験（EmEditor）:

- 登録した語の位置（先頭になる読み、2 番目になる読み）。`low` にした語の位置。学習で先頭に来ること。
- 「ありがとう」で絵文字が 6 番目あたりに出る。「ぞう」「く」で珍しい記号が最後にある。「ひえろぐりふ」で前に出る。
- 設定アプリで優先度を変えて保存し、`user_dict.toml` に `priority = "low"` が残る。`normal` に戻すと消える。

## 9. 決めたこと（2026-11-21、利用者）

1. 同じコストのときは、システム辞書を先にする。
2. 絵文字は、mozc に合わせて 6 番目に差し込む。
3. 最後の並びは「記号の残り → ひらがな・カタカナ → 珍しい記号」にする。
4. 珍しい記号の例外は、mozc と同じく、読みが「ひえろぐりふ」のときのヒエログリフだけにする。
5. この計画を `docs/Candidate_Order_Plan.md` に残す。
6. ユーザー辞書の語のコストの N は、`normal` の語だけを数える。
7. 設定アプリの編集の画面に、優先度の選択（「通常」「低」）を足し、保存のときにも残す。
8. `low` の語は、システム辞書の後ろ、LLM の候補の前に置く。

あわせて、ユーザー辞書の扱いを「学習するまで必ず先頭」から「コストで先頭を争い、負けたら 2 番目」に変えることにした（Step 12 の順の変更）。

## 10. 対象外

- LLM の候補を、辞書と同じコストの尺度で並べること。辞書のコスト（語の使われやすさ）と LLM の点数（読みと文脈から見た確からしさ）は意味が違い、釣り合わせるには変換の品質を測る仕組みが要る（#85）。
- 品詞のつながりのコスト（mozc のラティス）。辞書に品詞の番号とつながりの表を持たせることになり、LLM で変換する作りと合わない。
- 抑制単語（システム辞書の語を出さなくする指定）。新しい機能として別に扱う。
- 単漢字（#84）。
- 記号の説明の列（同じ種類の記号を途中で切らない決まり）。辞書の形式と `dict_schema` を変えることになる。
