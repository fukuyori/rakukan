# 日本語入力エンジンのための日本語理解モデル

## 要旨

本稿は、Rakukan の長文変換、文節分解、候補生成を再検討するための理論ノートである。直接の目的は、「長文で変換結果が尻切れになる」という表面的な問題に対して、単純な句読点分割や文字数ベースの chunk 化ではなく、日本語の形態素、文節、文法、意味理解、そして実用 IME の設計を踏まえた検討基盤を作ることである。

本稿で扱う問いは四つである。第一に、日本語の形態素解析はどこまで可能で、何を解いていないのか。第二に、IME に必要な日本語文法とは何か。第三に、会話やかな入力のように漢字表記がまだ与えられていない段階で、人間はどのタイミングで意味を組み立てているのか。第四に、azooKey はこの難問に対してどのように実用的な品質を確保しているのか。

結論を先に述べる。Rakukan が今後、本格的な長文変換へ進むなら、必要なのは「長い読みを短く切る」処理ではない。必要なのは、かな列から複数の語候補を列挙し、品詞・活用・接続・学習・文脈評価を組み合わせ、候補経路として保持する構造である。文節境界は文字列規則ではなく、語と語の接続可能性、機能語の結合、内容語のまとまり、候補の消費範囲、そして利用者が編集できる単位として決まる。

したがって、Rakukan に必要な次の研究段階は、単独の文節分割ヒューリスティックではなく、辞書・接続コスト・候補経路・学習・ライブ変換・候補表示を一つの理論モデルとして扱うことである。

## 1. 問題設定

日本語入力エンジンは、表面上は「かなを漢字かな交じり文へ変換する」ソフトウェアに見える。しかし内部で解いている問題は、単純な文字列置換ではない。利用者が入力するのは、しばしば漢字のない読み列である。そこには語境界も、品詞も、漢字表記も、意味の曖昧性解消も、文節境界も明示されていない。

たとえば次の入力を考える。

```text
にわにはにわにわとりがいる
```

この読み列は、ただちに一意の語列を与えない。

```text
にわ / には / にわ / にわとり / が / いる
庭 / には / 二羽 / 鶏 / が / いる
```

人間は、この読みを聞いたとき、逐次的に仮説を作る。「にわ」は「庭」かもしれない。「には」が続けば「庭には」という句が立つ。しかし次の「にわ」は、前と同じ「庭」かもしれないし、「二羽」かもしれない。さらに「にわとり」が続くことで、「二羽鶏」ではなく「二羽 / 鶏」という解釈が浮上する。最後に「がいる」が来ることで、「鶏がいる」という述語構造が成立する。

ここで重要なのは、理解が文末で一括して起こるのではない点である。人間は入力の途中で複数の仮説を持ち、後続情報で仮説を強化・棄却・修正する。IME も同じ問題に直面する。入力時点では漢字表記が与えられていないため、語境界と表記を同時に推定しなければならない。

Rakukan の現在の問題は、この複雑な推定問題を十分に構造化しないまま、長い読み全体を変換対象として扱う場面にある。LLM や辞書に長い読みを渡すだけでは、出力が途中で切れる、候補が文脈と合わない、候補表と本文 composition がずれる、学習が期待通り効かない、といった問題が起きる。これを句読点や文字数だけで切ると、症状は軽減するかもしれない。しかし、それは言語的な根拠を持つ解決ではない。

本稿では、Rakukan が本当に進むべき方向を検討するため、次の四領域を整理する。

1. 日本語形態素解析の能力と限界。
2. IME に必要な日本語文法。
3. ひらがな列・音声列から意味が構築される過程。
4. azooKey が実用品質を確保するために採用している構造。

## 2. 日本語形態素解析はどこまでできるか

### 2.1 形態素解析が解く問題

形態素解析は、文を形態素という単位へ分割し、各単位に品詞、活用、原形、読みなどの情報を付与する処理である。MeCab の典型的な出力では、表層形に対して品詞階層、活用型、活用形、原形、読み、発音が付与される。たとえば「すもももももももものうち」は、「すもも / も / もも / も / もも / の / うち」のように解析される。

この処理は、日本語の空白なし表記に対して非常に有効である。文章中に空白がないため、どこで語を切るかは自明ではない。形態素解析器は辞書を引き、候補語を列挙し、それらを接続コストで評価して最適な経路を選ぶ。

MeCab はこの問題を、辞書、連接表、未知語処理、コスト推定、Viterbi 探索として定式化している。辞書項目は表層形、左文脈 ID、右文脈 ID、単語コストを持ち、連接表は前件の右文脈 ID と後件の左文脈 ID の組に対する接続コストを持つ。解析時には、入力文に対して辞書候補を配置し、前後の接続コストと単語コストを足し合わせ、最小コストの経路を探す。

これは「語として存在するか」だけでなく、「前後に接続して自然か」を評価する仕組みである。たとえばある文字列が辞書にあるとしても、前後の品詞や活用との接続が不自然なら、経路全体としては高コストになる。逆に、単語単体の頻度が少し低くても、文全体として自然な接続を作るなら選ばれやすくなる。

### 2.2 形態素解析は意味理解そのものではない

形態素解析は強力だが、意味理解そのものではない。解析器は、表層文字列を辞書項目列へ対応づけ、品詞や活用情報を付ける。しかし、それだけで文の意味を完全に理解したことにはならない。

「庭には二羽鶏がいる」という文を考える。形態素解析器は「庭」「に」「は」「二」「羽」「鶏」「が」「いる」のような候補列を作り得る。しかし、「二羽鶏」という複合語をどう扱うか、「二羽 / 鶏」と読むのか、「庭には / 二羽 / 鶏がいる」という文節構造をどう見るかは、辞書・品詞・接続コスト・意味的な自然さの相互作用で決まる。

通常の形態素解析器は、すでに漢字かな交じりになった文を入力とすることが多い。この条件では、漢字表記が大きな手がかりになる。「庭」と「二羽」は表記上区別される。しかし IME が扱う入力は、まだ「にわ」の段階である。この段階では、表記の区別が消えている。したがって IME の問題は、通常の形態素解析より難しい。

IME は、読み列から語境界、品詞、表記、意味候補を同時に推定する。形態素解析器が「漢字かな交じり文から形態素列を求める」ものだとすれば、かな漢字変換器は「かな列から形態素候補列と表記候補列を同時に求める」ものである。これは、解析と生成が重なった問題である。

### 2.3 UniDic の短単位と長単位

日本語の「単位」は一種類ではない。UniDic は、コーパス注釈のために短単位を重視する。短単位は、語の内部構造を比較的細かくそろえて扱うための単位であり、形態素解析の辞書項目として使いやすい。一方で、利用者が IME の候補操作で直感的に扱いたい単位は、短単位そのものとは限らない。

たとえば「東京都立大学」や「情報検索」のような語は、短単位では複数要素に分かれるかもしれない。しかし検索インデックス、予測変換、IME の候補表示では、より大きなまとまりとして扱いたい場合がある。Sudachi が A/B/C の分割モードを持つのは、この粒度の違いが実用上重要だからである。細かい分割が常に正しいわけでも、粗い分割が常に正しいわけでもない。用途によって必要な単位が変わる。

IME における文節は、短単位や形態素と同一ではない。文節は、典型的には自立語に付属語が続くまとまりである。たとえば「学校に」「行きます」は、形態素としては「学校 / に」「行き / ます」に分かれるが、文節としては「学校に」「行きます」と扱うほうが自然である。候補選択や文節移動では、この「利用者が操作したい意味上のまとまり」が重要になる。

### 2.4 形態素解析の限界

形態素解析の限界は、少なくとも四つある。

第一に、入力表記に依存する。漢字かな交じり文を解析する場合と、全ひらがな列を解析する場合では難しさが違う。漢字は語境界や意味の強い手がかりになる。全ひらがなではその手がかりが失われる。

第二に、辞書に依存する。辞書にない固有名詞、新語、専門用語、俗語、造語は未知語処理に回る。未知語処理は字種や統計に基づいて候補を作れるが、既知語と同じ精度で意味や品詞を当てられるわけではない。

第三に、品詞体系に依存する。品詞の粒度、活用分類、接続 ID の設計によって、解析結果は変わる。日本語文法として妥当でも、辞書の品詞体系が十分でなければ、その妥当性をスコアへ反映できない。

第四に、文脈・談話・常識の理解には限界がある。形態素解析は局所的な語列の自然さを扱うが、会話の状況、話者の意図、世界知識、長距離依存を完全には扱わない。IME の候補順位では、局所接続だけではなく、利用者の履歴、直前の確定、ドメイン、アプリ文脈なども重要になる。

したがって、Rakukan が形態素解析を取り入れる場合、それだけで「日本語理解」が完成するとは考えないほうがよい。形態素解析は基盤であり、候補経路を作るための構造である。その上に、文節構成、候補ランキング、学習、文脈評価、ユーザー操作との整合が必要になる。

## 3. IME に必要な日本語文法

### 3.1 文法は実装上の制約である

日本語文法は、単なる説明体系ではない。IME にとって文法は、候補を捨てる、候補を上げる、境界を決める、学習対象を選ぶ、部分確定を安全に行うための制約である。

たとえば、助詞は単独で文節を作りにくい。助詞は前の自立語に付く。助動詞も、活用語に接続して意味や時制・態・丁寧さを加える。したがって、形態素単位で「学校 / に / 行き / ます」と切れたとしても、IME の文節操作では「学校に / 行きます」と扱うのが自然である。

一方で、すべての機能語を機械的に前へ結合すればよいわけでもない。複合助詞、連語、引用、並列、挿入、固有名詞、数詞、助数詞、記号、英数字混在などがある。文節境界は、語種と接続に基づくが、利用者の編集可能性も考慮しなければならない。

### 3.2 自立語と付属語

日本語の文節を考えるうえで基本になるのは、自立語と付属語である。自立語は、それ自体で文節の中心になれる語である。名詞、動詞、形容詞、副詞、連体詞、接続詞、感動詞などがこれにあたる。付属語は、自立語に付いて文法的意味を加える語である。助詞、助動詞が典型である。

文節は、おおまかには次のような構造を持つ。

```text
文節 = 自立語 + 付属語*
```

「私 は」「学校 に」「行き ます」のように、付属語は前の自立語へ接続する。この構造は、IME の候補表示や文節移動と相性がよい。利用者は「は」だけを独立候補として選びたいのではなく、「私は」というまとまりを見たいことが多い。

しかし、かな漢字変換ではさらに難しい問題がある。読み列の時点では、自立語と付属語の境界が見えない。たとえば「には」は、「に + は」とも、語の一部とも読める。「では」「とは」「から」「まで」「として」「について」なども、複合的な付属語として働く場合がある。IME は、辞書候補と接続可能性から、それらを候補経路として扱わなければならない。

### 3.3 活用と接続

動詞、形容詞、形容動詞、助動詞は活用する。活用は、後続する語を制約する。たとえば動詞の連用形には「ます」「た」「て」などが続きやすい。未然形には「ない」「れる」「せる」などが続く。終止形・連体形は文末や名詞修飾に関わる。

IME において活用は二重に重要である。第一に、候補語の列挙に関わる。読みが「いきます」のとき、「行き + ます」という候補を作るには、「行く」の連用形「行き」と助動詞「ます」の接続を認識する必要がある。第二に、文節境界に関わる。「行きます」は形態素としては二つでも、文節としては一まとまりである。

活用を無視すると、語としては存在するが文法的に不自然な候補が残る。逆に、活用接続を適切に評価できると、かな列から自然な語列を選びやすくなる。

### 3.4 助詞の役割

助詞は日本語理解の中心的な手がかりである。格助詞は名詞句と述語の関係を示す。「が」は主語・対象、「を」は目的語、「に」は場所・方向・時点・対象、「で」は場所・手段・原因などを示す。係助詞「は」「も」などは話題や対比を作る。接続助詞は節と節を結ぶ。

かな入力では、助詞はしばしば曖昧性解消に効く。「にわには」の「には」は、前の「にわ」が名詞である可能性を強める。「とりがいる」の「がいる」は、前が生物名詞や存在対象である可能性を強める。助詞は短いが、境界の強い手がかりである。

ただし、助詞を単純な区切り記号として扱うのは誤りである。助詞は前の語に付く付属語であり、文節の一部である。「庭 / には」ではなく「庭には」と見るほうが、IME の文節操作として自然である。したがって助詞は「切る場所」ではなく、「前の自立語を文節として閉じる方向の手がかり」として扱うべきである。

### 3.5 複合語と固有名詞

複合語と固有名詞は、文節解析の難所である。「情報検索」「自然言語処理」「東京都立大学」「山田太郎」「新大阪駅」のような表現は、内部に複数の語を含む。しかし実用上は一つのまとまりとして扱いたいことが多い。

細かく切れば辞書照合や統計には便利かもしれない。しかし IME の候補操作では、過剰分割が利用者の負担になる。逆に粗くまとめすぎると、未知語や専門用語に弱くなる。

ここで重要なのは、単位の多層性である。内部的には短単位や形態素を保持しつつ、表示・候補・文節操作ではより大きなまとまりを出せるようにする。azooKey が候補に辞書要素列を保持することは、この多層性と関係する。候補文字列だけでは、あとからどこが語境界で、どの部分が学習対象で、どこが文節境界かを復元しにくい。

### 3.6 係り受けと意味

文節解析だけでは、完全な意味理解には届かない。日本語の意味構築には係り受けがある。「太郎は二郎を見た女性に渡した」のような文では、どの文節がどこに係るかで意味が変わる。IME の通常変換では、完全な係り受け解析まで常時行うのは重い。しかし、局所的な文節境界と候補順位には、係り受けの初歩的な情報が影響する。

たとえば「赤い花を見た」は、「赤い」が「花」に係る。「昨日学校に行った」は、「昨日」が述語へ係る。「庭には二羽鶏がいる」では、「庭には」が場所・話題、「二羽」が数量、「鶏がいる」が存在述語を作る。こうした構造は、単語ごとの辞書コストだけでは十分に表現できない。

ただし、IME の設計では、すべてを意味解析に任せるべきではない。まずは形態素・品詞・接続コストで候補経路を作り、学習と文脈評価で順位を調整し、ユーザー操作で修正できる構造にする。そのうえで、必要なら LLM やニューラル評価を reranker として使う。この順序が安全である。

## 4. ひらがな列から意味はいつ組み立てられるか

### 4.1 会話は漢字列ではない

人間の会話では、漢字は流れてこない。聞き手が受け取るのは音声の連続である。そこには空白も漢字もない。日本語母語話者は、それでもほぼリアルタイムに意味を理解する。

この事実は、IME にとって重要である。IME の入力も、漢字表記が確定する前は音声に近い。ローマ字入力であれ、かな入力であれ、内部的には読み列が形成される。利用者はその読み列を見ながら、途中のライブ変換や候補表示で意味を確認する。

人間は、音声列を聞くとき、まず音韻的な単位を処理し、語候補を立て、文法的に接続できる候補を残し、文脈で解釈を絞る。重要なのは、これが逐次的に行われることである。最後まで待ってから全体を解析するのではなく、途中で仮説を作る。

### 4.2 逐次仮説としての理解

「きょうはあめがふるかもしれない」という発話を聞くとする。最初の「きょう」は「今日」と解釈される可能性が高い。「は」が来ると話題化される。「あめ」は「雨」か「飴」か曖昧だが、「がふる」が続くことで「雨」が強くなる。「かもしれない」が続くと、断定ではなく可能性の表現になる。

この過程では、後続情報が前の解釈を修正する。「あめ」だけでは複数候補があるが、「降る」が来れば「雨」が選ばれる。人間は、前の候補を完全に確定せず、ある程度の曖昧性を保持している。

IME も同じである。ライブ変換で早く候補を出すことは重要だが、早すぎる確定は危険である。途中の読みで候補を出しつつ、後続入力で更新できなければならない。これは候補経路の保持、差分再計算、prefix completion、文節単位確定と関係する。

### 4.3 意味理解の階層

ひらがな列から意味を組み立てる過程は、少なくとも次の階層に分けられる。

```text
音韻・かな列
  -> 語候補
  -> 品詞候補
  -> 形態素列候補
  -> 文節候補
  -> 係り受け候補
  -> 文脈・談話上の意味
```

IME が常に全階層を完全に解く必要はない。しかし、どの階層を使っているのかを設計上明確にする必要がある。

文字数ベースの分割は、この階層を無視する。句読点ベースの分割は、句読点がある文には効くが、句読点がない会話的入力には効かない。助詞だけを見る分割は、付属語の機能を誤解しやすい。正しい方向は、語候補と品詞接続に基づいて候補経路を作り、文節はその経路から導くことである。

### 4.4 後続情報による再解釈

日本語理解では、後続情報による再解釈が頻繁に起きる。これは IME のライブ変換で特に重要である。

たとえば「はし」を入力した段階では、「橋」「箸」「端」などが候補になる。「をわたる」が続けば「橋」が強くなる。「でたべる」が続けば「箸」が強くなる。「のほう」が続けば「端」が強くなる。このとき、前半の候補を固定しすぎると、後続文脈で自然な解釈に変えられない。

したがって、ライブ変換の内部状態は「現在表示している候補」だけでなく、「どの読み範囲を消費している候補か」「どの辞書要素列から来た候補か」「後続入力で再評価可能か」を保持する必要がある。候補文字列だけを持つ設計では、後から意味的に再構成するのが難しい。

### 4.5 人間の理解と IME の違い

人間は、常識、状況、話者、前後の会話、視覚情報を使う。IME は通常、そこまでの情報を持たない。したがって、IME は人間の理解を完全に再現するのではなく、機械的に利用できる手がかりを組み合わせる。

利用できる手がかりは次のようなものだ。

- 辞書にある語候補。
- 品詞・活用・接続コスト。
- 語の頻度や単語コスト。
- ユーザー辞書。
- 学習履歴。
- 直前に確定した文節。
- 現在の入力範囲。
- アプリやフィールドの文脈。
- LLM やニューラル評価による候補 reranking。

ここで LLM は、自由生成器として使うと危険である。候補の消費範囲や学習対象が不明になり、尻切れや幻覚、候補表との不整合が起きやすい。むしろ、辞書・ラティスが作った候補経路を評価する reranker として使うほうが IME と相性がよい。

## 5. azooKey はどのように実用品質を確保しているか

### 5.1 単純な文字列変換ではない

azooKey の重要な点は、かな文字列から候補文字列を返す単純な関数ではなく、入力管理、辞書検索、ラティス、Viterbi、候補契約、学習、予測、デスクトップ側セッション管理を組み合わせた構造を持つことである。

Rakukan の既存分析メモでは、azooKey の特徴として次が挙げられている。

- 入力履歴と表示文字列を分離して持つ。
- 候補が消費する入力範囲を持つ。
- 候補が辞書要素列と学習可否を持つ。
- 通常候補、予測候補、英語予測、先頭文節候補を分離する。
- 辞書は単語表記と読みだけでなく、接続 ID と品詞的情報を持つ。
- 学習履歴はユーザー辞書と別のデータとして管理される。
- ニューラル評価層は候補生成を置き換えるだけでなく、候補評価や制約付き探索に関わる。

この構造は、IME の実用品質を支える。実用品質とは、単に第一候補が当たりやすいことだけではない。入力途中で破綻しないこと、候補選択が安定すること、部分確定後に残りを変換できること、学習が候補順位に効くこと、OS 側の marked text と内部状態がずれないことも含む。

### 5.2 ラティスと Viterbi

azooKey の通常変換は、辞書候補をラティスに配置し、接続コストを使って候補経路を評価する。これは、形態素解析器と同じ基本構造である。

入力文字列の各位置から辞書候補を引き、その候補が入力のどの範囲を覆うかをノードとして持つ。各ノードは前のノードと接続し、単語コスト、接続コスト、学習補正などを足し合わせる。終端ノードから経路をたどることで、候補文字列だけでなく、辞書要素列、消費範囲、最終状態を持つ Candidate が復元される。

ここで重要なのは、候補が文字列ではなく経路である点だ。候補文字列「今日は雨が降る」だけでは、どの部分が「きょう」、どの部分が「あめ」、どの部分が「ふる」に対応するかが失われる。辞書要素列を保持していれば、学習、文節境界、prefix completion、部分確定、候補更新に使える。

### 5.3 入力 index と surface index の二重性

azooKey は入力履歴上の位置と表示文字列上の位置を分けて扱う。これは、ローマ字入力、typo correction、prefix completion、文節編集で必要になる。

ローマ字入力では、入力キー列と表示かな列の長さが一致しない。「kyo」は「きょ」になる。typo correction では、入力側と表示側の対応がさらに単純でなくなる。文節編集では、候補が表示文字列の何文字を消費したかと、元の入力要素のどこまでを消費したかが両方必要になる。

この dual index は、IME の実用性に直結する。単純な文字列置換モデルでは、候補の消費範囲が曖昧になる。消費範囲が曖昧だと、先頭文節だけを確定した後に残りを継続変換する、文節境界を伸縮する、候補表と marked text を同期する、といった操作が壊れやすい。

### 5.4 候補契約

azooKey は候補を用途別に分ける。通常候補、予測候補、英語予測、先頭文節候補は、同じ候補文字列でも意味が違う。通常候補は現在の入力全体を変換する。予測候補は入力より長い表現を提案する。先頭文節候補は、部分確定や prefix completion と結びつく。

この分離は、UI と変換コアの契約である。候補一覧に出ている文字列が、入力全体を置き換えるものなのか、先頭だけを確定するものなのか、予測として入力外を含むものなのかが明確でなければ、確定時の挙動が不安定になる。

Rakukan の候補表示問題でも、候補が「どの reading に対応するか」を持つことが重要だった。候補表の第一候補、本文 composition、選択位置がずれると、利用者は何が確定されるのか分からなくなる。azooKey 型の候補メタデータは、この問題に対する実用的な答えである。

### 5.5 文節境界は CID の語種分類に基づく

azooKey の文節境界は、単純な文字列規則ではない。辞書ストアの `wordTypes` は CID から大まかな語種を得る。分類には BOS/EOS、preposition、core、postposition があり、`isClause(former,latter)` はこの語種を見て文節境界を判定する。

これは重要である。文節境界を「助詞の前で切る」「句読点で切る」「一定文字数で切る」といった規則にすると、言語構造を見ていない。azooKey は、辞書要素が持つ接続 ID と語種情報を使い、文節境界を候補経路上の性質として扱う。

さらに、この文節境界は複数箇所で使われる。first clause results、学習メモリの文節 bigram、文節編集、prefix completion などである。つまり文節境界は一箇所の UI 都合ではなく、変換器全体の横断構造である。

### 5.6 学習はユーザー辞書追記ではない

azooKey の学習は、単純なユーザー辞書追記ではない。学習は単語、文節、候補全体など複数粒度を扱い、保存と forget も考慮する。さらに、学習対象にしてよい語とそうでない語を判定する。

助詞、助動詞、接頭辞、接尾辞、記号などを無差別に学習すると、学習メモリが汚れる。IME の学習は、利用者の選択をそのまま辞書へ追加すればよいわけではない。どの単位を学習すべきか、どの文脈で効かせるべきか、時間経過でどう減衰させるかが必要になる。

Rakukan でも、ライブ変換の確定内容をそのままユーザー辞書へ入れることは避ける方針が確認されている。これは正しい。学習は、候補経路や文節単位と結びついて初めて安定する。

### 5.7 差分変換とキャッシュ

実用 IME は、毎回全文をゼロから変換していては遅い。azooKey は差分変換、キャッシュ復元、prefix completion を持つ。前回入力と lattice を再利用できる場合、必要な部分だけを再計算する。

ただし、差分変換は意味論そのものではない。意味論は full conversion に戻せる必要がある。差分変換は最適化であり、結果が full conversion と矛盾してはならない。この分離は重要である。

Rakukan のライブ変換も、速度と品質の間で同じ問題を持つ。ライブ変換は軽い beam で早く候補を出し、Space 変換は候補数を広げる、といった設計がある。しかし、ライブ変換と Space 変換で意味の違う区切り規則を持つと、候補表と本文がずれる。したがって、高速化は意味論の外側に置くべきである。

### 5.8 ニューラル評価層の位置づけ

azooKey には Zenzai のようなニューラル評価層がある。しかし、これは辞書・ラティス・候補契約を不要にするものではない。むしろ、symbolic candidates を生成したうえで、それらを評価・補助する位置づけで読むべきである。

これは Rakukan にとって重要である。LLM を自由生成器として使うと、出力が入力範囲をどこまで消費したのか、どの辞書要素に対応するのか、学習してよいのか、候補表と本文をどう同期するのかが曖昧になる。ニューラル層は、構造化された候補の上で働かせる方が安全である。

### 5.9 azooKey から得られる教訓

azooKey の実用品質は、単一の賢いアルゴリズムから生まれているのではない。複数の不変条件が積み重なっている。

- 入力履歴と表示文字列を分ける。
- 候補に消費範囲を持たせる。
- 候補に辞書要素列を残す。
- ラティスと接続コストで候補経路を評価する。
- 文節境界を CID/語種に基づいて判定する。
- 候補種別を分ける。
- 学習対象を選別する。
- 差分変換を最適化として扱う。
- OS 層は core 状態を表示へ反映する役に徹する。

Rakukan が文節分解へ進むなら、この全体構造を理解せずに「文節っぽく切る」実装へ進むべきではない。

## 6. Rakukan への示唆

### 6.1 現状の強みと限界

Rakukan は、TSF DLL と engine-host を out-of-process 化し、GPU リソースを engine-host 側で管理する構造を持つ。ライブ変換、候補表示、学習履歴、ユーザー辞書、MOZC バイナリ辞書、LLM 変換などの要素がすでにある。v0.8 系では CandidateView の導入、ライブ変換 preview のランキング反映、pending update の選択位置維持など、候補表示の安定化も進んでいる。

一方で、長文変換の理論基盤はまだ弱い。既存の `rakukan.dict` は読み、表記、コストを中心に扱うが、Mozc 本体のような lid/rid、connection matrix、候補経路、文節境界、学習単位を十分に保持しているわけではない。したがって、現状のまま「長文を論理的に分節する」には材料が足りない。

### 6.2 非方針の確認

既存の cleanup plan は、次を非方針としている。

- 全入力を一律 chunk 化する。
- LLM プロンプトだけで対象範囲制約を保証したことにする。
- ライブ変換と Space 変換で別々の区切り規則を持つ。
- 変換後文章の形態素解析結果から入力ひらがな境界を復元する。
- 助詞や表層文字による当て推量で分割する。
- 独自理論で実用 IME 相当の変換器を作る。

本稿の立場は、この非方針と一致する。長文シリキレに対して、句読点分割や文字数分割は短期的な回避策にはなり得るが、本質的ではない。文節境界を扱うには、読み列から候補経路を作る構造が必要である。

### 6.3 Rakukan が目指すべき段階

Rakukan が本格的に長文変換を改善するなら、段階は次のように分けるべきである。

第一段階は、理論調査と現状差分の明確化である。MeCab、Sudachi、UniDic、Mozc、azooKey がどの単位を持ち、どのコストを使い、どの情報を候補へ残すかを整理する。ここではまだ実装しない。

第二段階は、辞書要素の情報拡張である。少なくとも、候補が読み、表記、コストだけでなく、品詞的分類、左/右接続 ID、学習可否、語種、消費範囲を持てるかを検討する。

第三段階は、ラティス生成の実験である。全機能を IME に入れる前に、CLI またはテスト用モジュールで、かな列から候補経路を作り、Viterbi 的に N-best を出す実験を行う。

第四段階は、文節境界の導出である。候補経路上の語種・接続 ID から、どこを文節境界と見るかを決める。これは文字列規則ではなく、候補経路の属性から導く。

第五段階は、候補契約の拡張である。候補文字列だけでなく、消費 reading 範囲、辞書要素列、文節範囲、学習対象、候補種別を TSF 側へ渡す。

第六段階は、ライブ変換と Space 変換の統合である。ライブ変換は軽量な探索で早く preview を出し、Space 変換は候補幅を広げる。しかし、両者が同じ候補構造を共有するようにする。

第七段階は、学習と文節 bigram である。確定した候補をどの粒度で学習するか、機能語を学習対象から外すか、文節間の接続をどう記録するかを決める。

### 6.4 形態素解析器をそのまま使う問題

外部形態素解析器をそのまま使えば解決するわけではない。理由は三つある。

第一に、多くの形態素解析器は漢字かな交じり文を入力とする。Rakukan が必要なのは、ひらがな列からの候補生成である。

第二に、形態素解析器の出力単位は IME の文節操作単位と一致しない。形態素を文節へまとめる構成ルールが必要になる。

第三に、外部解析器が出した結果を変換後 surface から逆算して reading に戻すのは危険である。入力 reading のどこに対応するかを失うと、部分確定や学習が壊れる。

したがって、形態素解析器は、補助として使うなら有用だが、Rakukan の中心には「reading から候補経路を作る」構造が必要である。

### 6.5 LLM の役割

Rakukan は LLM 変換を持つ。これは強力だが、長文変換の主構造にするには注意が必要である。

LLM は、文脈や意味の評価に強い。しかし、IME では候補の消費範囲、候補の辞書要素列、学習対象、文節境界、N-best、部分確定、再変換が必要である。LLM の自由出力は、これらを自然には提供しない。

したがって、LLM は次の位置づけが望ましい。

- 辞書・ラティス候補の reranker。
- 候補が少ない場合の補助候補生成。
- 長文全体の文脈評価。
- 文節列の候補順位調整。
- 未知語や固有名詞の候補補完。

逆に、LLM の自由出力だけで変換対象範囲や文節境界を決めるのは避けるべきである。

## 7. 研究課題

### 7.1 形態素解析能力の評価

まず調べるべきことは、既存形態素解析器が「かな列」に対してどこまで使えるかである。漢字かな交じり文ではなく、ひらがな入力を対象にする。

評価対象:

- MeCab + IPADic。
- MeCab + UniDic。
- Sudachi。
- Mozc 辞書または Mozc 本体。
- azooKey の辞書構造。

評価観点:

- かな列から候補語を列挙できるか。
- 品詞と活用が得られるか。
- 接続コストを利用できるか。
- N-best を得られるか。
- 文節境界を導けるか。
- 候補が reading 範囲を保持できるか。
- 未知語処理が IME に適するか。

### 7.2 日本語文法モデルの整理

次に、Rakukan が内部で必要とする簡略文法モデルを整理する。

必要な分類:

- 内容語。
- 助詞。
- 助動詞。
- 接頭辞。
- 接尾辞。
- 記号。
- 数詞・助数詞。
- 固有名詞。
- 動詞活用語尾。
- 形容詞活用語尾。

必要な関係:

- 自立語 + 付属語。
- 活用形 + 助動詞。
- 名詞 + 助詞。
- 数詞 + 助数詞。
- 接頭辞 + 名詞。
- 名詞 + 接尾辞。
- 文頭・文末接続。

ただし、これは独自の日本語理論を作るという意味ではない。既存辞書の品詞体系と接続 ID を利用し、Rakukan の実装で必要な抽象化を作るという意味である。

### 7.3 ひらがな列理解のモデル化

第三の課題は、ひらがな列から意味候補を組み立てる過程をモデル化することである。

このモデルでは、入力全体を一つの候補にするのではなく、複数の仮説を保持する。

```text
reading
  -> word hypotheses
  -> POS hypotheses
  -> lattice paths
  -> clause candidates
  -> conversion candidates
  -> ranked display candidates
```

重要なのは、途中で一つに決めないことである。人間の理解と同じように、後続情報で候補を更新できる必要がある。

### 7.4 azooKey 実用構造の移植可能性

第四の課題は、azooKey の構造のうち、Rakukan に移植すべき概念と、移植しない概念を分けることである。

移植候補:

- Candidate の消費範囲。
- 辞書要素列の保持。
- first clause candidates。
- CID/語種に基づく文節境界。
- 学習対象の選別。
- prefix completion。
- dual index。

慎重に扱うもの:

- azooKey 固有の辞書形式。
- Desktop 側セッション構造。
- Zenzai との統合。
- モバイル IME 前提の予測設計。

Rakukan は Windows TSF と out-of-process engine-host を持つため、azooKey の構造をそのまま移植するのではなく、概念を Rakukan の責務境界へ合わせる必要がある。

## 8. 提案する論理モデル

### 8.1 基本方針

Rakukan の将来モデルは、次の原則を持つべきである。

1. 変換単位は文字数で決めない。
2. 文節境界は候補経路の属性から導く。
3. 候補は文字列だけでなく消費範囲と辞書要素列を持つ。
4. ライブ変換と Space 変換は同じ候補構造を共有する。
5. LLM は構造化候補を評価する補助層に置く。
6. 学習は文節・語・候補経路の粒度を区別する。
7. 部分確定は候補範囲に基づいて行う。

### 8.2 データモデル

概念的には、次のデータが必要になる。

```text
ReadingSpan
  start
  end

LexicalCandidate
  reading_span
  surface
  base_form
  pos
  conjugation_type
  conjugation_form
  left_id
  right_id
  word_cost
  source
  learnable

PathCandidate
  elements: Vec<LexicalCandidate>
  total_cost
  connection_costs
  surface
  reading_span
  clause_boundaries

ClauseCandidate
  reading_span
  surface_span
  element_range
  selected_candidate_index

ConversionCandidate
  surface
  reading_span
  clauses
  elements
  candidate_kind
  score
```

このモデルでは、文節は最初から文字列として切り出すものではない。候補経路の上に、文節境界を重ねる。これにより、同じ reading に対して複数の文節解釈を持てる。

### 8.3 処理フロー

処理フローは次のようになる。

```text
input update
  -> reading buffer
  -> lexical lookup for all spans
  -> lattice construction
  -> Viterbi / N-best
  -> clause boundary derivation
  -> candidate restoration
  -> ranking / learning / LLM reranking
  -> TSF candidate view
```

ライブ変換では、探索幅を絞る。Space 変換では、探索幅と候補数を広げる。しかし、どちらも同じ `ConversionCandidate` 構造を返す。

### 8.4 文節境界の導出

文節境界は、次のような情報から導く。

- 前後の語種。
- 自立語と付属語の関係。
- 接続 ID。
- 活用形。
- 記号・句読点。
- 数字ラン。
- 学習済み文節 bigram。
- 候補経路上のコスト差。

ここで重要なのは、助詞の前で切るのではなく、助詞を前の自立語へ結合する方向を基本にすることである。助詞は文節の境界標識であると同時に、文節内部の付属語である。この両面を区別する必要がある。

### 8.5 部分確定

部分確定は、文字位置ではなく `ClauseCandidate` に基づくべきである。確定対象の文節がどの reading 範囲を消費しているか、どの surface 範囲を表示しているか、どの辞書要素列を持つかが必要になる。

確定後は、残りの reading span から新しい変換状態を作る。ここで重要なのは、残りを単なる文字列として再入力するのではなく、既存の候補経路や prefix completion を利用できる形で継続することである。

句読点入力は、通常の文節理解とは別に、安全制約として扱う。利用者が「、」または「。」を入力した時点で、その直前までの未確定変換は確定し、入力された「、」「。」自身も確定状態に置く。これにより、「、」「。」を含んだ長い reading を LLM へ問い合わせない。句読点は変換対象範囲を広げるための文字ではなく、直前までの変換対象を閉じる境界として扱う。

これは根本的な分節解析による変換を導入する前の暫定対策である。この処理は、句読点を文節境界として正解推定するものではなく、LLM 問い合わせ範囲を安全に閉じるための入力イベント処理に限る。将来的には、辞書・品詞・接続コスト・候補経路に基づく分節解析へ置き換える。

この処理は自動確定とは区別する。句読点が入力されたときに確定されるのは、利用者が明示的に句読点を入力した結果であり、IME が無入力状態で勝手に確定するわけではない。また、Enter による確定操作とは別の入力イベントであるため、Enter の意味を変えない。

### 8.6 学習

学習は三層に分ける。

第一に、語学習である。特定の reading に対して特定の surface を上げる。

第二に、文節学習である。文節単位の候補選択を記録し、次回同じ文節で効かせる。

第三に、文節間学習である。隣接文節の bigram を記録し、文脈内の候補順位へ効かせる。

助詞や助動詞そのものを単独で学習対象にすると、学習が汚れやすい。機能語は、文節内の接続や文節 bigram の一部として扱うほうが安全である。

## 10. 追加考察: 「理解」と「変換」を分けて考える

### 10.1 IME は意味を完全理解する必要があるのか

ここで一度、重要な問いを立てる必要がある。IME は日本語の意味を完全に理解する必要があるのか。

答えは「完全には必要ない。しかし、意味理解に近い情報を部分的に扱えなければ実用品質には届かない」である。IME の目的は、文章の真偽を判定したり、話者の意図を完全に解釈したりすることではない。目的は、利用者が入力しようとしている表記を、少ない操作で、予測可能な形で提示することである。

しかし、表記候補は意味と無関係ではない。「あめがふる」は「雨が降る」であって「飴が降る」ではない。「はしでたべる」は「箸で食べる」であって「橋で食べる」ではない場合が多い。ここでは、述語や助詞が名詞候補の意味を絞っている。IME がこれを全く扱えなければ、候補順位は不自然になる。

つまり IME に必要なのは、哲学的・談話的な完全理解ではなく、候補順位に効く範囲の意味的制約である。これは、語の品詞、語彙カテゴリ、接続可能性、共起、学習履歴、文節関係、文脈評価として実装される。意味は、実装上は「候補経路のスコア差」として現れる。

### 10.2 「表記の復元」と「意味の復元」

かな漢字変換では、表記の復元と意味の復元が絡み合う。読み「こうしょう」は、「交渉」「高尚」「校章」「公称」「考証」など多くの候補を持つ。表記候補を選ぶには、周辺文脈が必要になる。

しかし、IME がまず扱うべきなのは、意味そのものではなく、意味を区別できる候補構造である。候補構造がなければ、後からどれが文脈に合うかを評価できない。

たとえば次の入力を考える。

```text
こうしょうがながびく
```

この場合、「交渉が長引く」が自然である。ここで「こうしょう」の候補を一つに固定するには、後続の「長引く」が効いている。したがって、変換器は「こうしょう」単体の候補を持つだけでなく、「こうしょう / が / ながびく」という経路全体で評価しなければならない。

一方、次の入力では別の候補が上がる。

```text
こうしょうなぶんしょう
```

ここでは「高尚な文章」が自然である。「な」が形容動詞語幹との接続を示し、「文章」が後続することで「高尚」が強くなる。つまり同じ読みでも、後続する助詞・助動詞・名詞・述語によって候補順位が変わる。

この例は、文字列分割では解けない。必要なのは、複数候補を保持し、後続文脈で経路全体を評価することである。

### 10.3 人間の聞き取りと IME の候補経路

人間の聞き取りでは、音声が曖昧でも文脈で補われる。雑音があっても、文法的にあり得る語列や文脈上自然な語が選ばれる。この処理は、IME の候補経路探索と似た構造を持つ。

ただし、人間の処理はより広い。話者の癖、前の会話、世界知識、場面、視線、共有知識が使われる。IME はそれらを直接持たない。だから IME は、人間の理解を完全再現するのではなく、機械的に利用できる情報を整える必要がある。

そのために必要なのが、辞書、接続コスト、学習、文節候補、候補メタデータである。これらは、人間の意味理解の縮小版ではない。IME が扱える形へ落とした「意味の足場」である。

### 10.4 文節は認知上の単位でもある

文節は、文法上の単位であると同時に、利用者が IME 上で操作する単位でもある。利用者は、変換後に左右キーで文節を移動したり、Shift+矢印で文節を伸縮したり、先頭文節だけを確定したりする。この操作単位は、形態素単位より粗く、文全体より細かい。

「私は学校に行きます」を例にする。

```text
形態素: 私 / は / 学校 / に / 行き / ます
文節:   私は / 学校に / 行きます
```

形態素単位で候補を移動すると、利用者は助詞や助動詞だけを何度も通過しなければならない。文全体単位だけだと、部分的な誤変換を直せない。文節は、この中間の実用単位である。

したがって、Rakukan が文節分解を導入するなら、「文節とは何か」を単なる学校文法の定義としてではなく、利用者操作と候補管理の単位として定義する必要がある。文節は、内部的には候補経路上の範囲であり、UI 的には選択・確定・再変換の単位である。

### 10.5 「正解率の高い区切り」とは何か

ユーザーが求めているのは、正解率の高い区切りである。しかし、ここでいう正解率は単純ではない。文法的に正しい区切り、利用者が編集したい区切り、変換候補として高品質な区切りは、完全には一致しない。

たとえば「東京都立大学に行く」は、内部的には「東京 / 都立 / 大学 / に / 行く」と解析できるかもしれない。しかし IME の文節操作では「東京都立大学に / 行く」と扱いたい場合が多い。検索用途なら「東京」「都立」「大学」へ分けたいこともある。固有名詞としては「東京都立大学」が一単位である。

したがって「正解率の高い区切り」とは、単一の gold standard ではなく、用途に依存する。Rakukan で必要なのは、IME 操作としての正解である。これはおおむね次の条件を満たす。

- 付属語は前の自立語に結合される。
- 固有名詞や複合名詞は過剰に分割されない。
- 誤変換箇所を利用者が修正しやすい。
- 先頭文節確定後に残りを自然に変換できる。
- 候補表の範囲と本文 composition の範囲が一致する。
- 学習対象が文節や内容語として妥当である。

この意味で、文節境界の評価には、単なる解析精度だけでなく、操作性の評価が必要である。

## 11. 追加考察: 形態素解析器と IME の違い

### 11.1 入力方向が違う

形態素解析器と IME は、似ているが入力方向が違う。形態素解析器は、通常、すでに表記された文を解析する。IME は、まだ表記されていない読みから表記を生成する。

形態素解析器:

```text
漢字かな交じり文
  -> 形態素列
  -> 品詞・原形・読み
```

IME:

```text
読み列
  -> 形態素候補列
  -> 表記候補列
  -> 候補順位
```

この違いは大きい。形態素解析では、表層文字列が辞書引きのキーになる。IME では、読みが辞書引きのキーになる。漢字表記の手がかりがないため、同音異義語が大量に出る。

### 11.2 辞書のキーが違う

形態素解析辞書では、表層形が辞書項目の入口であることが多い。IME 辞書では、読みから表記候補を引く必要がある。したがって、辞書の索引構造が異なる。

Mozc や azooKey のような IME 系の辞書は、読み prefix から候補を列挙することが重要になる。入力途中でも候補を出すため、完全一致だけでなく prefix search が必要になる。さらに予測変換では、入力より長い候補も扱う。

Rakukan の `rakukan.dict` が読み・表記・コストを持つことは出発点として有用である。しかし、長文変換や文節分解には、読み prefix 検索、接続 ID、品詞的分類、候補の消費範囲、未知語処理が必要になる。

### 11.3 N-best の意味が違う

形態素解析の N-best は、解析候補を複数出すために使われる。IME の N-best は、利用者に候補一覧を出すために使われる。この二つは似ているが、表示要件が違う。

IME の候補一覧では、候補同士が見た目に分かりやすく、選択後の動作が安定していなければならない。候補が入力全体を消費するのか、先頭文節だけを消費するのか、予測として未入力部分を含むのかを区別する必要がある。

したがって、IME の N-best は単なる経路順位ではなく、候補契約と結びつく。候補には kind、reading span、surface span、辞書要素列、学習可否が必要になる。

### 11.4 文節境界は後処理ではない

形態素解析器の出力を後から文節にまとめることはできる。しかし IME では、文節境界は後処理に留まらない。先頭文節候補、部分確定、学習、prefix completion、候補表示に関わるため、文節境界は候補生成の途中から意識されるべきである。

後から surface だけを見て文節境界を復元しようとすると、reading との対応が壊れる。たとえば「今日は雨が降る」という surface から、「きょうは / あめが / ふる」に対応する reading 範囲を確実に戻すには、変換時の対応情報が必要である。

したがって、文節境界は候補経路の属性として保持するのがよい。surface 文字列の再解析ではなく、reading から作った経路の上で境界を持つ。

### 11.5 未知語処理の違い

形態素解析の未知語処理は、字種や文脈から未登録語を推定する。IME の未知語処理は、それに加えて表記候補を作る必要がある。

たとえば未知の固有名詞をひらがなで入力した場合、IME はそれをひらがなのまま出す、カタカナにする、ローマ字由来として扱う、ユーザー辞書候補を探す、学習履歴を見る、といった選択肢を持つ。未知語を「名詞」として扱うだけでは不十分である。

このため、Rakukan の未知語処理では、字種、読み、カタカナ化、英数字、ユーザー辞書、学習履歴、LLM 補助を分けて考える必要がある。

## 12. azooKey 詳細観察: 実用性を支える不変条件

### 12.1 不変条件 1: 候補は消費範囲を持つ

azooKey 型設計の第一の不変条件は、候補がどの入力範囲を消費するかを持つことである。これは、候補表示、確定、部分確定、prefix completion の基礎になる。

候補が消費範囲を持たない場合、Enter で何を確定するのかが曖昧になる。候補表には「今日は雨」と出ているが、内部 reading は「きょうはあめが」まで進んでいる、という状態が起きると、候補表と本文 composition の意味がずれる。Rakukan が CandidateView を導入した背景も、この問題に近い。

消費範囲は、単なる文字数ではない。ローマ字入力や typo correction では、入力要素と表示かなの対応がずれる。したがって、input index と surface index の両方が必要になる。

### 12.2 不変条件 2: 候補は辞書要素列を失わない

候補文字列だけを残すと、後続処理が困る。学習対象、文節境界、予測、候補の由来、接続 ID が失われるからである。

azooKey は Candidate に辞書要素列を残す。これにより、「この候補はどの語から構成されたか」を後で使える。文節 bigram を作る、機能語を学習対象から外す、first clause を取り出す、といった処理が可能になる。

Rakukan が LLM 変換を使う場合も、できれば LLM 出力を候補文字列としてだけ扱わず、対応する辞書要素列または少なくとも reading span と segment metadata を持たせる必要がある。完全な辞書要素列が得られない場合は、候補の信頼度や学習可否を下げる設計も考えられる。

### 12.3 不変条件 3: 文節境界は一箇所で定義する

文節境界の定義が複数箇所に分散すると、ライブ変換、Space 変換、候補表、学習、部分確定で挙動がずれる。これは IME として非常に危険である。

azooKey の分析では、文節境界は `DicdataStore.isClause` から first clause results、learning memory、segment editing、prefix completion へ影響する横断構造として整理されている。これは重要な設計姿勢である。

Rakukan でも、もし文節境界を導入するなら、TSF 側の一時的な句読点処理やライブ変換専用規則としてではなく、engine 側の候補構造から導かれる共通の境界にするべきである。

### 12.4 不変条件 4: 高速化は意味論を変えない

差分変換、キャッシュ、ライブ変換の軽量 beam は、性能最適化である。これらは変換意味論を変えてはならない。azooKey の差分変換が full conversion に戻せる必要があるのと同じで、Rakukan のライブ変換も Space 変換と同じ候補構造に接続している必要がある。

もしライブ変換だけ独自の区切り規則を持つと、ライブ preview では自然に見えたものが Space 候補表で別の意味になる。逆に Space 変換では候補が出るがライブ変換では途中で切れる、という不整合も起きる。

したがって、ライブ変換は「同じ意味論の軽量実行」であるべきで、「別の変換器」になってはならない。

### 12.5 不変条件 5: OS 層は意味を作らない

TSF や marked text API は、表示と確定のための層である。文節境界や候補意味を OS 層で作ると、engine と UI が乖離する。

azooKey Desktop の `SegmentsManager` は OS 層との境界に位置するが、候補や composing text の構造を core 側から受け取り、それを表示へ反映する役割として読める。Rakukan でも、TSF 層は候補構造を表示し、選択・確定を engine へ伝える責務に寄せるほうが安全である。

もちろん TSF 層には composition lifecycle、timer、candidate window、focus、DocumentMgr など Windows 固有の難しさがある。しかし、そこで日本語文法を作り始めると保守不能になる。文法・候補・文節は engine 側、表示・入力イベント・確定は TSF 側、という境界を守るべきである。

- 現行辞書形式のフィールド一覧。
- Mozc 元データとの差分。
- 追加すべき辞書属性の候補。
- 辞書サイズ・ロード時間への影響見積もり。

完了条件:

- ラティス探索に必要な情報が現行辞書に足りるか判断できる。
- 足りない場合、どの情報をどこから持ってくるか候補がある。

### 13.3 Phase R2: かな列ラティス実験

TSF へ入れる前に、CLI またはテスト crate でかな列ラティスを実験する。目的は UI ではなく、候補経路の品質確認である。

成果物:

- `reading -> lexical candidates -> lattice -> N-best` の実験コード。
- ベンチマークかな列。
- 正解候補と候補順位の比較。
- 接続コストなし/ありの比較。

完了条件:

- 代表例で、文字数分割より意味のある候補経路が得られる。
- 処理時間が IME 用に改善可能な範囲にある。

### 13.4 Phase R3: 文節境界導出

ラティス経路から文節境界を導く実験を行う。ここでは、形態素列をそのまま文節にしない。自立語 + 付属語、語種分類、接続 ID、記号、数字ランを使って文節を構成する。

成果物:

- 文節境界導出ルール。
- `is_clause_boundary` 相当の設計。
- first clause candidates の試作。
- 文節単位の表示例。

完了条件:

- 「私は学校に行きます」が `私は / 学校に / 行きます` に近い単位で扱える。
- 複合名詞の過剰分割をある程度抑制できる。
- 助詞だけを独立文節にしない。

### 13.5 Phase R4: Candidate 契約拡張

候補が reading span、surface span、辞書要素列、文節範囲、候補種別を持つように契約を設計する。これは TSF 表示と engine の境界に関わる。

成果物:

- `ConversionCandidate` 設計。
- `CandidateView` 拡張案。
- 既存候補表との互換方針。
- ログ probe の設計。

完了条件:

- 候補表の選択候補と本文 composition が同じ候補 ID または同じ span に基づいている。
- partial commit の対象範囲を候補から決められる。

### 13.6 Phase R5: ライブ変換統合

最後に、ライブ変換へ統合する。ここでは高速化と意味論を分ける。ライブ変換は探索幅を制限して早く候補を返すが、候補構造は Space 変換と同じものにする。

成果物:

- ライブ変換用軽量探索設定。
- Space 変換用候補幅設定。
- 両者の候補構造一致テスト。
- stale preview 防壁との統合。

完了条件:

- ライブ preview と Space 候補表の第一候補が不自然に乖離しない。
- 長文でも候補の消費範囲が明示される。
- 尻切れ候補が出た場合、候補構造上で検知・降格できる。

## 14. 用語整理

### 14.1 形態素

意味や文法機能を持つ最小に近い単位。IME の操作単位とは限らない。

### 14.2 短単位

UniDic などで使われる、コーパス注釈に適した細かい語単位。形態素解析に向くが、IME の文節操作には細かすぎることがある。

### 14.3 文節

自立語に付属語が付いたまとまり。IME では候補移動、部分確定、再変換の単位として重要。

### 14.4 候補経路

reading 全体または一部を覆う辞書要素列。表記候補はこの経路から復元される。

### 14.5 接続コスト

前後の語がどれだけ自然に接続するかを表すコスト。品詞、活用、語種の制約を数値化したもの。

### 14.6 reading span

候補が入力読みのどの範囲を消費するかを表す範囲。部分確定や候補同期に必要。

### 14.7 surface span

候補が表示文字列のどの範囲に対応するかを表す範囲。ローマ字入力や typo correction では reading span と単純対応しない。

### 14.8 first clause candidate

入力全体ではなく、先頭文節だけを対象にした候補。部分確定や prefix completion に関わる。

### 14.9 prefix completion

先頭部分を確定したあと、残りの入力状態を継続する処理。IME の体験では、確定と次の変換が自然につながる必要がある。

### 14.10 reranker

候補生成後に候補順位を調整する層。LLM やニューラル評価は、自由生成器ではなく reranker として使うと候補契約を保ちやすい。

## 15. 研究上の注意

### 15.1 独自文法を作らない

Rakukan が独自の日本語文法を作るべきではない。必要なのは、既存辞書・品詞体系・形態素解析理論・IME 実装を理解し、Rakukan の責務境界に合わせて抽象化することである。

独自の助詞ルールや文字列規則を積み上げると、最初は動いて見えても、例外が増えるたびに破綻する。日本語の文法現象は広く、例外も多い。実用 IME は、単発ルールではなく、辞書、接続コスト、学習、候補経路で柔らかく評価する。

### 15.2 「それっぽい分割」を避ける

句読点、助詞、文字数、一定長の chunk は、実装しやすい。しかし、それだけでは文節理解ではない。助詞は境界の手がかりだが、助詞自身は前の語に付く。句読点は明示的な区切りだが、句読点のない入力も多い。文字数は言語的根拠が薄い。

したがって、これらは補助情報として使うことはあっても、主判断にしてはいけない。

### 15.3 「変換後解析」を主経路にしない

LLM や辞書で一度 surface を作り、その surface を形態素解析して文節を復元する案は危険である。surface から reading 対応を戻すのが難しく、誤変換があると解析結果も誤る。さらに、候補経路の情報が失われる。

文節は、変換後 surface から復元するのではなく、reading から候補経路を作る段階で持つべきである。

### 15.4 評価を UI 体験と結びつける

文節分解の評価は、解析器の正解率だけでは足りない。IME では、利用者が修正しやすいか、候補表が理解しやすいか、部分確定後に残りが自然につながるか、学習が効くかが重要である。

したがって、評価セットには「第一候補が正しいか」だけでなく、次を含めるべきである。

- 文節移動回数。
- 誤変換修正に必要なキー操作数。
- 部分確定後の残り候補品質。
- ライブ変換と Space 変換の一致。
- 学習後の順位変化。
- 候補表と本文 composition の同期。

### 15.5 小さく入れるなら観測から

実装へ進む場合も、最初から変換経路を置き換えない。まず観測用の候補 metadata、辞書情報の棚卸し、CLI 実験、ログ probe から始める。TSF のライブ変換はクラッシュや stale preview のリスクがあるため、理論実験と UI 統合を分けるべきである。

この方針は、Rakukan の既存の安定化方針とも一致する。ライブ変換を壊さず、候補表と composition の同期を守り、段階的に進める。

### 15.6 研究成果を実装判断へ翻訳する

理論研究は、実装から切り離された知識で終わってはいけない。Rakukan にとって必要なのは、理論を読んだという事実ではなく、設計判断が変わることである。たとえば、文節境界を考えるときに「助詞で切る」と言わず、「助詞は付属語なので前の自立語に結合する。ただし候補経路上では、その直後が次文節開始候補になり得る」と説明できることが重要である。

同じように、形態素解析器を導入するかどうかを考えるときには、「MeCab を使えば文節が分かる」と言わない。MeCab は主に表層文の形態素解析器であり、IME が必要とする reading からの表記候補生成とは向きが違う。使うなら、辞書・品詞体系・連接コスト・未知語処理のどの部分を借りるのかを明確にする必要がある。

azooKey を参照するときも、「azooKey のようにする」とだけ言わない。どの不変条件を借りるのかを分ける。候補の消費範囲、辞書要素列、first clause candidates、CID による語種判定、学習対象の選別、差分変換の位置づけ、OS 層との責務分離。それぞれは独立した設計判断である。

したがって、この研究の実装上の成果は、最終的には次の形に落ちるべきである。

- 文節境界を一時的な UI 規則にしない。
- 候補文字列だけでなく、候補の由来と範囲を保持する。
- ライブ変換と Space 変換の候補意味論を分けない。
- LLM 出力は、候補契約を満たす場合だけ学習や部分確定に使う。
- 外部辞書や解析器を使う場合、reading からの候補生成に必要な情報を失わない。

この翻訳作業ができて初めて、理論研究は Rakukan の品質改善に接続する。

もう一つ重要なのは、研究成果を「できること」と「まだできないこと」に分けて記録することである。日本語理解の理論を学んだからといって、すぐに実用 IME 相当の文節解析を自作できるわけではない。むしろ、理論を理解するほど、辞書、コーパス、接続コスト、未知語処理、評価セット、ユーザー操作ログが必要であることが見えてくる。これは悲観材料ではなく、設計上の安全装置である。

Rakukan では、理論理解を段階的な判断へ変換する。今ある情報で安全にできることは候補 metadata の観測、辞書情報の棚卸し、CLI 実験である。まだ危険なことは、TSF ライブ変換の本線に文節推定を直接入れること、句読点や助詞だけで自動分割すること、LLM 出力を根拠なく学習対象にすることである。この区別を維持することで、研究は実装を急がせる圧力ではなく、実装を正しい順序に並べるための基盤になる。

この意味で、本稿は最終仕様ではない。むしろ、今後の議論で安易な案を退け、どの追加調査が本当に必要かを判断するための物差しである。以上を出発点とする。継続調査で更新する予定。

## 16. 結論

Rakukan の長文変換問題は、単純な長文処理問題ではない。根本には、日本語入力エンジンが避けて通れない、かな列から語・品詞・文節・意味候補を組み立てる問題がある。

日本語形態素解析は、この問題の一部を解く。辞書、品詞、活用、接続コスト、Viterbi 探索は、候補経路を作るための強力な基盤である。しかし、通常の形態素解析は漢字かな交じり文を対象にすることが多く、IME が扱うひらがな列からの候補生成とは問題が異なる。

日本語文法は、IME にとって実装上の制約である。自立語と付属語、助詞と助動詞、活用と接続、複合語と固有名詞、文節と係り受けを理解しなければ、文節境界はただの文字列分割になる。

人間の日本語理解は、逐次仮説の構築と更新である。会話では漢字が流れてこない。それでも人間は音声列から語候補を立て、文法と文脈で意味を絞り、後続情報で解釈を修正する。IME もこの性質を反映し、候補を早く出しつつ、後続入力で再評価できる構造を持つ必要がある。

azooKey は、実用 IME としてこの問題に構造で答えている。入力履歴と表示文字列の分離、ラティスと Viterbi、接続コスト、辞書要素列を持つ候補、候補種別の分離、文節境界の語種判定、学習メモリ、差分変換、ニューラル評価層の位置づけ。これらはすべて、単なる第一候補品質だけでなく、入力途中の安定性、部分確定、候補表示、学習、OS 連携を支える。

Rakukan が次に進むべき方向は、句読点分割や文字数 chunk 化ではない。必要なのは、reading から候補経路を作り、その経路に文節境界と学習と候補契約を載せることである。これは大きな研究課題であり、すぐに実装へ進むべきではない。しかし、この理論を理解せずに小手先の分割を重ねるより、ここで一度立ち止まり、IME としての日本語理解モデルを築くことが、長期的には正しい。
