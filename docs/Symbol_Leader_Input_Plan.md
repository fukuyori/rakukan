# リーダー記号（… ⋯ ‥）の入力方式: 検討記録

作成: 2026-09-09

位置づけ: PR #31（記号の連打を三点リーダーへ畳む）のレビューから派生した検討の記録。**すべて検討段階で、実装には進んでいない。**

関連: Issue #18 の G（記号）、`docs/Step10_Romaji_Rebuild_Plan.md` §3.3 / §4.4

関連 Issue: #35（本件の問題点の記録）、#34（問題点 4: `z` + 記号で未確定ローマ字が残る）、PR #31

## 1. 経緯

- PR #31 は `。。。` `・・・` `、、、` `...` を打鍵中に `⋯`（U+22EF）へ自動で畳む opt-in 機能（`input.symbol_repeat_ellipsis`、既定 off）。
- レビューで次が判明した。
  - engine の trie にある `z.` → `…`、`z,` → `‥`、`z/` → `・`、`z[` `z]` → `『` `』` は、TSF が `.` `,` `/` `[` `]` を `direct_input_symbol` で記号入力経路（`on_punctuate` → `push_raw`）へ回すため、**キーボードからは到達不能**（`z` + `,` は「、z」になる。ログで確認済み）。
  - 主要 IME（MS-IME / Google 日本語入力 / ATOK）は打鍵中の自動置換をせず、読みからの変換候補か専用キー列（`z.`）で出す。出力は JIS X 0208 内の `…`（U+2026）で、`⋯`（U+22EF）を出す IME は確認できていない。
  - 自動置換には「元に戻す」操作が必須で（`。。。` をそのまま入れたい場合がある）、PR #31 の「Backspace で `⋯` を 1 回で消す」設計では戻せない。
  - PR #31 は畳んだとき `romaji_input_log` を `⋯` に書き換えるため、Step 10 の不変条件（log + pending == 打鍵列）と衝突する。

## 2. 決めたこと

### 2.1 文字の割り当て

| 打鍵 | 出力 | 備考 |
|---|---|---|
| `。。。` + Space、`z.` | `…`（U+2026） | 標準の三点リーダー。他 IME と同じ |
| `・・・` + Space、`z/` | `⋯`（U+22EF） | 中央寄せ。JIS X 0208 外だが利用者の明示操作でのみ出る |
| `・・` + Space、`z,` | `‥`（U+2025） | 二点リーダー。用途は限定的（会話の間、リーダー線） |
| `、、、` | 対象外 | 読点の打ち間違いを巻き込むため |

英字直後の `...` / `．．．` は `。。。` と同じ `…`。

### 2.2 方式は 2 本立て、自動置換は採らない

| 方式 | 発見可能性 | 位置づけ |
|---|---|---|
| 記号だけの読みを Space で変換（候補: そのまま / `…` / `⋯` / `‥`） | 高い。IME の通常操作で見つかる | **本線**。設定不要、戻す操作不要、学習で 2 回目以降は Space 1 回 |
| `z.` `z/` `z,`（`z[` `z]`） | 低い。説明が必要 | 近道。設定画面の「キー名の一覧と注意」と README に記載する前提 |

打鍵中の自動畳み込み（PR #31 方式）は、戻す操作の問題が解消しないため採らない。

## 3. 設計の要点

### 3.1 記号だけの読みを変換対象にする（本線）

現状の仕組み（`crates/rakukan-tsf`）:
- `text_util::split_by_punctuation` は区読点 1 文字ごとに `(reading, Some(punct))` を作る。`。。。` は `("",。)` ×3 になる。
- `on_convert.rs` のブロック分割変換は、全ブロックの reading が空なら何もせず `return`。文中の区読点のみブロックは「候補なしで残す」。
- 結果、`。。。` は単独でも文中でも変換に乗らず、ユーザー辞書に読み `。。。` を登録しても引かれない。

変更案:
- 連続する区読点を 1 つの「記号 run」として扱う。run 長が 1 のときは現行どおり直前ブロックの `trailing_punct` にする（挙動不変）。run 長が 2 以上のときは `reading = run` の独立ブロックにし、候補を付ける。
- 記号 run ブロックの候補: 先頭は「そのまま」、続けて対応表（`。。。` → `…`、`・・・` → `⋯`、`・・` → `‥`）とユーザー辞書（読み = 記号列）。LLM は呼ばない。
- 確定時の学習キーは記号列そのもの。学習で `…` が先頭に上がる。
- `split_by_punctuation` の戻り値の変更は `on_convert.rs` の呼び出し 1 か所と `state.rs` のテストに影響する。
- ライブ変換は区読点で終わる読みでは起動しないので、Space 専用の挙動になる。

#### 3.1.1 具体化（2026-09-09 検討、判断待ち）

操作の流れ（現行のブロック分割変換に当てはめた場合）:

| 場面 | 操作 | 結果 |
|---|---|---|
| `。。。` だけを打って Space | 記号ブロック 1 つが選択状態 | 候補「そのまま / … / ⋯」。Enter で先頭候補を確定 |
| `そう。。。` を打って Space | ブロックは「そう」「。。。」の 2 つ。フォーカスは先頭 | `…` を選ぶには → で記号ブロックへ移動して候補を選ぶ |
| 学習後の `そう。。。` + Space | 記号ブロックの先頭候補が `…` | → で移動しなくても Enter で「騒…」 |

文中では初回だけ → による移動が要る。標準の区読点分割変換と同じ操作で、新しい操作は増えない。

決めるべき点と推奨:

- **A. 候補の並び**
  - 案 1: 「そのまま」を常に先頭。安全だが、学習しても Space 1 回では `…` にならない。
  - 案 2: 学習・ユーザー辞書の候補 → そのまま → 対応表。一度選べば文中でも Enter だけで `…`。`。。。` のまま入れたいときは候補から選び直す。
  - 推奨: 案 2。
- **B. 学習の粒度**
  - 現行の学習は読み全体 → 確定文全体（`そう。。。` → `騒…`）で、ブロック単位では学習しない。案 2 の「学習で先頭に上がる」は `。。。` を単独で変換して `…` を選んだ場合にだけ効く。
  - (a) 現行のまま（単独変換で 1 回学習すれば以後は文中でも効く）、(b) 記号ブロックだけ確定時にブロック単位で学習を追加。
  - 推奨: (a) で始め、実機で不便なら (b)。
- **C. 対象の範囲**
  - 同じ区読点が 2 文字以上連続し、対応表かユーザー辞書・学習に候補がある run だけを独立ブロックにする。候補が無い連続（`、、` `！！` など）と異なる記号の連続（`。・`）は現行どおり。既存の分割動作は変わらない。
  - 対応表: `。。。` / `...` / `．．．` → `…` `⋯`、`・・・` → `⋯` `…`、`・・` → `‥`。
- **D. ユーザー辞書との関係**: 記号列の読みでユーザー辞書を引く前提。設定アプリで読み `。。。` の登録が通るかは実機未確認（コード上は読みの文字種を検証していないように見える）。
- **E. 影響範囲**: TSF のブロック分割変換（`text_util.rs` の分割後処理、`on_convert.rs` のブロック生成）に閉じる。engine のローマ字状態・打鍵ログには触れないので Step 10 と独立。ライブ変換（区読点終端では起動しない）、ESC 復帰は現行のまま。

判断待ち: A（案 2 で良いか）、B（現行粒度で良いか）、C（範囲と対応表で良いか）。

### 3.2 `z` + 記号を trie に流す（近道）

- `dispatch.rs`: `Input(c)` で `direct_input_symbol(c)` が `Some` でも、engine の未確定ローマ字（`current_preedit().pending_romaji`）がちょうど `z` なら `on_input`（trie）へ流す。それ以外は現行どおり `on_punctuate`。
- `rules.rs`: `z/` を `・` から `⋯` に変更。`z.` → `…`、`z,` → `‥`、`z[` `z]` → `『` `』` は現行どおり。
- `text_util::is_kuten` に `…` `‥` `⋯` を追加する（`z.` で読みに入るようになるため。変換対象から外し、LLM に渡さない区切りとして扱う）。3.1 の候補として確定する場合は確定文字列に入るだけなので、この追加は 3.2 のためだけに必要。
- Backspace: trie が `…` を 1 出力として作るので `RemovedOutput` で 1 回で消え、log の `"z."` も 1 要素で整合する。

### 3.3 Step 10 との関係

- 3.2 は Step 10 §4.4「未確定ローマ字を追い越す入力」の特殊ケース（pending が `z`）で、先行して小さく入れられる。
- `z` 以外の pending（`k` + `.` → 「。k」、`j` + `.` → 「j。」）は §4.4 本体で扱う。順序は `flush_pending_n` → 残りを素通しで閉じる → 記号追記。
- Step 10 計画書 §3.3 に TSF の `direct_input_symbol` 経路を追い越し経路として追記し、§7.1 に `z,` = 「‥」、`z.` = 「…」、`k.` = 「k。」、`n.` = 「ん。」を加える（未反映）。

### 5.1 「。z」問題は 1 の決定に依存する

`z` + `.` が「。z」になる不具合（§1）は、直し方が 1 の判断で変わるため、単独では修正できない。

- `z` 系キー列を採用する場合: 未確定ローマ字がちょうど `z` のときだけ `.` `,` `/` `[` `]` を trie に流す振り分けが必要（`dispatch.rs`）。
- 採用しない場合: `z` も他の子音と同じく「`flush_pending_n` → 残りを素通しで閉じる → 記号を追記」（Step 10 §4.4）で扱う。`z` の特別扱いは不要で、入れると §4.4 と矛盾する。

したがって 1 が決まるまで「。z」は既知の不具合として残す。`z` 以外（`j` + `.` → 「j。」など。ログで確認済み）は方式に関係なく §4.4 の対象。
