#### 3-1 #55 spawn 後の接続失敗を `HostSpawnGuard` に数える

- 着手は #54 の修正後を推奨。段 2 の 1 週間の観測終了や実運用での発生を必須条件にせず、再現テストと修正を進める。修正を導入した場合は計測期間をビルドごとに区切る
- `try_connect_once` の失敗処理を共通化し、spawn 後の接続失敗と Hello / Create の失敗を、接続試行 1 回につき重複なく記録する
- 抑止中の接続失敗（500ms 待ち）は**数えないことを推奨**。抑止期限を延ばし続けないことを受入条件にする
- 回数は RPC 呼出回数と区別する。`call_with_retry_inner` → `ensure_connected` → `try_connect_once` の二重リトライで 1 RPC に最大 4 接続試行がある。失敗回数 3、集計窓 15 秒、抑止 30 秒の関係を時刻と試行数でテストする。「3 回目の RPC から」と固定しない
- テスト: 接続・spawn・時刻を制御し、spawn 失敗、spawn 成功後の接続失敗、Hello / Create 失敗、抑止中の既存ホストへの接続を確認。閾値到達後の追加 spawn が止まること、期限後に再試行できること、接続成功でカウンタがリセットされること、Shutdown 直後の再接続が回復することを確認する

#### 3-3 設定の全プロセス反映と、ホストへの古い設定の再送防止（J-5 の (2)、起票後）

- 現状: `Local\rakukan.engine.reload` は auto-reset で、1 回の Set で待機中の 1 プロセスだけが起きる。候補表示前の mtime 確認は `publish_atomics` で描画用などの複製値を更新し、`CONFIG_MANAGER` の current / last_modified は更新しない。IME 切替時の `reload_if_changed` は別経路
- **反映と巻き戻り防止を別の受入条件にする**。RPC に mtime を加えても、通知を受け取れなかった TSF のキャッシュ更新にはならない
- 方式は未決。全プロセスが変更を検出する仕組みと、設定を確定する主体を比較して決める。反映期限は「保存後の一定時間内」か「次の対象操作まで」かを設定の種類ごとに判断し、通知の取りこぼし・休止中のプロセスの追随方法を定義する
- 原案の `Create` / `ShutdownIfConfigDiffers` に mtime を載せる案は、変更検出の補助として再検討する。mtime を単調な版番号とはみなさず、同一 mtime で内容が異なる場合、以前の時刻のファイルへの復元、ファイル欠落・パース失敗、読込途中の更新を扱う。設定内容と版情報が同じ読込結果を指すことを保証する方法も必要
- ホスト再起動後に、新しい設定をどこから確定するかを決める。古いキャッシュの TSF が最初に `Create` した場合でも、先着順で古い設定を採用しないこと。ホストが現行ファイルを読む案などと比較し、プロセス内だけの新旧記録に依存しない
- 拒否・更新結果を TSF にどう返し、クライアントのキャッシュをどう追随させるかを定義する
- 現行で古い設定がホストへ再送される経路として重視するのは、再接続時に `try_connect_once` が保存済みの `config_json` で送る `Create`（`client.rs`）。この経路と `ShutdownIfConfigDiffers` に設定整合の規則を適用する
- RPC の `Reload`（`RpcEngine::reload()`、`client.rs:200`）は現行コードに呼び出し元が無い未使用経路。先に削除か存続かを判断し、残す場合に限って同じ設定整合の規則を適用する。`state.rs:393` の「`engine_reload()` が RPC Reload を使う」という古いコメントも、実装時に整理する
- テスト: 2 プロセス以上で新旧の設定を逆順に送る、ホスト終了後に古い側が先に接続する、通知を受けなかった側が後で操作する、連続保存、同一 mtime の変更、古いファイルへの復元、破損設定。正しい設定への収束と不要な再起動の連鎖が無いことを確認する
- 方式と反映期限の判断、上記の再現テストを #49 より先に確定し、実装・検証後に 3-4 を統合する。3-5 の読込失敗時の方針も、この設計と合わせて決める

#### 3-5 config 読込失敗の記録と、初期化・再読込時の扱い（J-5 の (1)、起票後）

- `ConfigManager::new` / `init_config_manager` の無警告な `unwrap_or_default()` を解消する。`init_config_manager` は `engine_reload_impl`（`state.rs:507`、設定アプリの保存通知 → `reload_watcher` → `engine_reload` の経路）と言語バーの「エンジン再起動」（`factory.rs:172`）からも呼ばれるため、起動時だけの問題として扱わない
- 影響は警告不足だけではない。コード上、読込失敗で既定値へ戻した後、その設定から `build_engine_config_json` でホストへの要求を作り、`shutdown_if_config_differs` へ送る。※推測です: ホストの設定と異なれば、既定値の設定によるホストの再起動・エンジンの再生成につながる。実機では確認していない
- ログは実際の処置を区別する。既定値へ戻した場合に、既存の再読込ログの「前の設定を維持した」という文面を流用しない
- 方針の推奨: 初回読込で有効な設定が無い場合は警告して既定値、稼働中の再読込失敗は警告して直前の有効な設定を保持する。未決事項として判断を受け、3-3 の版情報も失敗した読込で更新しないようにする
- テスト: 初回の破損設定、正常起動後の破損設定への変更、ファイル欠落、修復後の再読込。警告内容と有効な設定を確認する
- 再現・検証項目: 正常に動いている状態で config.toml を破損させ、設定アプリの保存通知（reload イベント）を送る。修正前にホストが既定値の設定で再起動・再生成されるかを、`rakukan.log` の `engine_reload` / `ShutdownIfConfigDiffers` とホストの PID・backend・モデル設定のログで確認し、修正後に直前の有効な設定が保たれることを確認する

2. run ごとに候補を作る。数字・記号 run は `literal_candidates`、かな run は変換器（数詞のかなには単位の漢字を足す）
3. `combine_runs` で連結し、件数を切り詰める
4. 連結後の文字列だけを `verify_digits_preserved` で検証する（`digits.rs:988`）
5. 重複を除き、残らなければ読みを返す

(c3) に必要な「その大字がどの run の候補から来たか」は、4 の時点で失われている。`verify_digits_preserved` と `combine_runs` の呼び出しは `digits.rs` 内だけ。

#### 決定

- **構造は A（生成元の持ち回り）**。`combine_runs` が候補と一緒に各文字の生成元（run の番号、かな run か）を返し、検証は連結後の文字列から数字を取り出す現行の解釈を維持する。生成元は、大字 1 文字 run を除外するかの判断にだけ使う
  - B（run ごとに検証）は採らない。連結で run の境目をまたぐ漢数字を、現行はひと続きの数として読む（`1じゅう` の `壱` + `十` → `壱十` = 10 となり、入力の 1 と合わず拒否）。B ではかな run の `十` だけを見て単位として許すため、この候補を通す
  - 既存の `combine_runs` は生成元付きの版を包む形にし、呼び出し 2 か所と既存テストを維持する想定
- **今回の対象範囲**: 除外の対象にする大字は `参` と `拾` に限る。`弐`（読み `に` が助詞に広く当たる）と `壱` は対象外
- **候補数制限の順序は維持**: 連結時の件数制限の後に検証する現行の順序は変えない
- **実装の受入条件（構造 A）**
  - `1じゅう` → `1十` は通し、`1じゅう` → `壱十` は拒否する
  - 数字 run 由来の大字は常に数値として数え、除外の根拠になる入力の読みを消費しない
  - 模擬比較の 38 組（33 組と追加の 5 組）の検証に加え、`combine_runs` が実際に作る生成元情報と検証処理を接続したテストを入れる

- **辞書を使う方式は採用候補として残す**。数詞エントリの扱いと探索方法が固まるまで、本実装への採用は保留する。構造 A は採用済みのまま

- **数詞エントリは除外の根拠から外す方針。方法は未確定**（→ 品詞の調査で材料不足と分かり、見直した。「判断の変更（2026-09-17、数詞エントリの扱い）」）
  - `拾番` の `拾` は数値として働くため、日常語中の大字の誤検出を直す規則で読み飛ばす対象にしない
  - かなから生成された数値（`拾番`、`十番`、`参枚` など）をどう保存・照合するかは、別の課題とする
  - 現行のバイナリ辞書は表記と cost だけを保持し、`lookup` もその 2 つを返す。数詞を識別する品詞情報は無い

- **順序の条件を入れ、探索順に依存しない判定にする**

  - 探索途中の失敗を候補全体の拒否にしない。この判定では、`参考と参考に2枚` は失敗する割当てがあっても、正当な割当てが存在するので通す（模擬検証の順序ありの全探索に「通す」が含まれていた）
  - 模擬検証の 1,502 µs は割当ての探索を含まない。実装方式を決める際に、同じ語が多数繰り返される場合も含め、探索込みの負荷を確認する

#### 3. 保持する場合の変更範囲（参考。上記のとおり #53 の対象は識別できない）

- **分類フラグで足りるか**: `名詞,数` の lid や rid の助数詞を 1 ビットずつのフラグに落とすことはできるが、`拾番` と `参考` を分けられないので、#53 の目的には足りない。通常の漢数字（`三枚`、`十番` などの別課題）に使うなら、フラグの定義を決めるために元の lid / rid を残す案も比較対象になる
- **builder**: `Entry` に lid / rid（またはフラグ）を足す。同じ読み・表記で品詞が違うエントリのまとめ方（最小 cost の品詞を残す・全部残す・フラグの和を取る）を決める。フラグを作るなら `id.def` の取得と読み込みが要る
- **辞書形式**: エントリを 8 バイトから広げる（lid / rid を u16 で持つと 12 バイト。インストール済み辞書の 1,139,177 エントリで約 4.3 MiB 増。フラグ 1 バイトでも境界合わせを含めて形式の変更になる）。`VERSION` を 1 から上げる
- **読込側**: `MozcDict` のヘッダー検証・エントリの読み出し・`lookup` の戻り値、`DictStore::lookup_class` などの呼び出し側
- **ID の版依存**: lid / rid の番号は `id.def` の版に結び付くので、MOZC のリビジョンを固定し、`rakukan.dict.build.json` に記録する必要がある（現状は master を取得し、記録していない）
- **辞書の再生成**: 形式を変えると既存の `rakukan.dict` は読めなくなるので、`install.ps1` の再生成判定（`$dictSchemaExpected`）と build info の更新が要る。インストーラー改修計画では辞書のビルドを `scripts/build-installer.ps1` 側へ移す予定なので、時期を合わせる必要がある
- 生成経路の記録（リビジョンの固定と記録、doc コメントの列の並びの誤り）は、分類情報を持たせるかどうかに関係なく残る課題

#### 判断の変更（2026-09-17、数詞エントリの扱い）

- **辞書方式を「入力の読みによって、その表記を正当化する方式」として継続する**

- **別課題**: 通常の漢数字（`十番`、`三枚` など）まで扱いを広げることは、今回は別課題とする
- **既知の制限**: 大字と通常の漢数字で結果が異なる。`2番と拾番` は `拾番` のエントリで通るが、`2番と十番`（`十` は除外の対象外）と `2枚と参枚`（`参枚` のエントリが無い）は拒否する

#### 方式

**前提（コードで確認した性質）**

- P1: 除外の対象は、`extract_digits` の取り出しで長さ 1 の漢数字 run（`参` / `拾`）になり、かな run の候補に属し、単位の読み飛ばしに当たらないもの。取り出しでは、漢数字 run は数字でも漢数字でもない文字、または数字で区切られる。run を数えるかどうかは、ほかの run の取り出し結果に影響しない（`after_digit` は数字と区切り文字でだけ変わり、漢数字 run では変わらない。単位の読み飛ばしの判定は、その run の文字・`after_digit`・入力の読みだけで決まる）
- P2: したがって、取り出した数字列は「固定の部分 F0」「対象 1 の数字列 d1（数えるときだけ入る）」「固定の部分 F1」…「対象 k の数字列 dk」「固定の部分 Fk」を順に連結したものになる。数字保存の判定は、この連結が入力の数字列と一致するかどうか
- P3: 使う組を出力の位置で並べると、非重複と順序の条件は、隣り合う組どうしの条件（`前.oj ≤ 後.oi`、同じ run なら加えて `前.rj ≤ 後.ri`）だけで全体が満たされる（各範囲で `i < j` なので推移的に成り立つ）。組 m が対象 t を覆い、m と重ならない組 m' が t より後の対象 t' を覆うなら、m' は出力上で m より後にある。run は出力上で連続しているので、別の run の組は出力の順に並ぶ
- P4: 1 つの組が複数の対象を覆う場合、全探索と同じく、同じ組を複数の対象に割り当ててよい（使う組の集合は同じ）。覆われている対象を割り当てないことも許す

**状態と遷移**

- 区切りの列 `F0, d1, F1, …, dk, Fk` を前から処理する。状態は `(j, last)`: `j` = 入力の数字列の照合済みの長さ、`last` = 直前に割り当てた組（無ければ なし）
- 固定の部分 F: 入力の `j` 文字目以降が F で始まれば `(j + |F|, last)` へ
- 対象 t の数字列 d:
  - 数える（割り当てない）: 入力の `j` 文字目以降が d で始まれば `(j + |d|, last)` へ
  - 除外する（組 m を割り当てる。m は t を覆う組）: `last` が なし、`last = m`、別の run で `last.oj ≤ m.oi`、同じ run で `last.oj ≤ m.oi` かつ `last.rj ≤ m.ri` のいずれかなら `(j, m)` へ
- 受理: 最後の区切りの後に `j = 入力の数字列の長さ` の状態があれば「通す」

**状態数の上限**: 区切りの数 S（= 2k + 1 以下）、入力の数字列の長さ L、組の数 M に対して、各区切りの後の状態は `(L + 1) × (M + 1)` 以下、全体で `(S + 1) × (L + 1) × (M + 1)` 以下。遷移は各状態から「対象を覆う組の数 + 1」以下。組の数 M は、かな run の読みの部分文字列の数（n(n+1)/2）× 読みごとの表記数（辞書で 1 読みあたり通常語 50 件以下）× 出力中の出現位置の数で上から抑えられ、入力の大きさの多項式になる。したがって、この方式は多項式時間で判定できる

**全探索と同じ結果になる理由**: P2 により、割当てが通るかどうかは「どの対象を除外したか」と「その割当てが非重複・順序を満たすか」だけで決まる。P3・P4 により、割当てが条件を満たすことは、対象を出力の順に見たときに、割り当てた組が直前に割り当てた組と上記の関係にあることと同値。状態 `(j, last)` は、ある区切りまでに「入力の先頭 j 文字と一致し、直前の組が last である、条件を満たす部分割当て」が存在することを表し、遷移はその部分割当ての延長をすべて列挙する。よって、受理状態に到達することと、全探索で通る割当てが存在することは同値（上記は設計上の整理。以下の照合で確認したが、証明として検証したものではない）

  - 変換ワーカー: `Engine::bg_start`（`lib.rs`）→ `conv_cache::start` → `worker_loop`（`conv_cache.rs`）。`Request` は変換器と変換パラメータだけを持つ。ホストの `InputChar` 要求でも `bg_start` が呼ばれる（`server.rs`）ため、ライブ変換では打鍵ごとに走りうる
- **候補の組み立て**: かな run は変換器、数字・英字・記号 run は `literal_candidates` で run ごとの候補を作り、`combine_runs` で連結して `limit`（= `num_candidates`）件に切り詰めた後、1 件ずつ `verify_digits_preserved` で検証する。検証後に重複を除く
- **辞書**: `DictStore::lookup_dict` は通常語の帯を返すが、呼ぶたびに debug ログを 1 行出す。MOZC 辞書本体（`DictStoreInner::mozc`）は `rakukan-dict` の外から見えない。`lookup_user` は呼ぶたびに `user_dict.toml` の更新を確認する。辞書は `engine_poll_dict_ready`（`ffi.rs`）で後から注入される
- **判定の単調性**: 動的計画法は「どの対象も除外しない」経路を含むので、現行の `verify_digits_preserved` が通す候補は必ず通す。現行が拒否する候補のうち、除外の対象を含むものだけが結果を変えうる

#### 1. 構造 A との接続

**生成元の保持**

- `combine_runs` に、連結した文字列と一緒に「run ごとの区間」を返す版を足す（例: `combine_runs_with_origin(run_candidates, limit) -> Vec<Combined>`、`Combined { text, parts: Vec<PartRef> }`、`PartRef { run: usize, cand: usize, char_start: usize, char_len: usize }`）。`cand` は `run_candidates[run]` の中の添字
- 既存の `combine_runs` はこれを呼んで `text` だけを返す形にし、全部リテラルの経路と既存テストを変えない
- 候補が空の run を読み飛ばす現行の挙動は、`parts` にも同じく反映する（空の run の区間は作らない）
- 重複の除去は、現行どおり検証の後に文字列で行う（同じ文字列で生成元の違う組み合わせがあっても、検証を通ったものが残る）

**数字抽出の共通化（判定規則を 1 か所にする）**

- 現行の `extract_digits` の走査を、数値の単位の列を返す 1 つの関数にまとめる（例: `scan_numeric_tokens(s, reading) -> Vec<NumericToken>`）
  - `NumericToken::Digit { pos, ch }`（算用数字・全角数字を正規化した 1 文字）
  - `NumericToken::KanjiRun { start, len, digits: Option<String>, unit_skipped: bool }`（`unit_skipped` は現行の「数字の直後の単位で、入力の読みが正当化する」判定。`digits` は `parse_kanji_number_digits` の結果）
- `extract_digits` は、このトークン列から `unit_skipped` でないものの数字列を連結するだけにする。現行の `verify_digits_preserved` の結果は変わらない（既存テストで確認）
- 除外の対象の判定も、このトークン列に対する 1 つの述語にする（例: `is_exclusion_target(token, parts)`: `KanjiRun` で `len = 1`、文字が `参` / `拾`、`unit_skipped` でない、`digits` がある、区間がかな run に属する）
- 動的計画法の入力（固定部分と対象の列）は、同じトークン列から作る。固定部分は対象以外のトークンの数字列の連結、対象はその数字列。取り出しと区切りの規則は `scan_numeric_tokens` だけが持つ

**動的計画法への受け渡し**

- 入力: 区切りの列（固定部分 / 対象）、対象ごとの対応候補の一覧、組の一覧（run、読みの範囲、出力の範囲）、入力の数字列
- 状態と遷移は、照合で検証した表現（`(j, last)`、`last = m` による同じ組の再利用を含む）をそのまま使う。`last` の圧縮は初回の実装に含めない
- 検証の流れ（候補ごと）
  1. 現行の判定（トークン列から作った数字列 = 入力の数字列）で通れば通す
  2. 現行判定で通らず、除外対象が無い、または辞書の参照手段が無い場合は拒否する（現行と同じ）
  3. それ以外は、未作成の照合表・出力位置の照合を必要に応じて作り、動的計画法で判定する（照合表が未作成という理由では拒否しない）

#### 2. 辞書の受け渡し

- **渡し方**: `convert_with_digit_protection` に「読みから表記を引く手段」を引数で渡す（例: `license_source: Option<&dyn SurfaceSource>`）。`SurfaceSource` は「読み（かなの部分文字列）→ 表記の一覧」だけを返す trait にし、テストでは固定の表で差し替えられるようにする
  - 同期経路: `Engine::convert` がエンジンの `dict_store.as_ref()` から作って渡す
  - 変換ワーカー: `bg_start` が `self.dict_store.clone()`（`Arc` の複製）を `Request` に入れ、`worker_loop` がそこから作って渡す。`DictStore` は `Send` / `Sync` で、`Drop` で I/O をしないので、既存の「エンジン DLL 内の BG スレッドや Drop で I/O をしない」制約に触れない
- **辞書の後からの注入**: `bg_start` の時点の `dict_store` を使う。注入前に始まった変換は辞書なしで判定され（現行と同じ）、注入後の変換から照合が効く。注入前に `Done` になった同じ読みの結果は、読みが変わって再変換されるまで残る（候補の辞書マージは取り出し時に行われるので、影響は数字保存の判定だけ）
- **辞書が無い場合**: 照合表を作らず、上記の流れの 2 で現行と同じ判定になる
- **システム辞書**: `rakukan-dict` に、ログを出さず、通常語の帯の表記だけを返す引き方を足す（例: `DictStore::lookup_system_normal(reading) -> Vec<String>`、件数の上限なし。現行の `lookup_dict` はログと上限があるので使わない）。検証済みの条件（表記 2 文字以上、`参` / `拾` を含む）での絞り込みは `rakukan-engine` 側で行う
- **ユーザー辞書**: 初回の根拠に含めない（判断済み）。検証したシステム辞書の通常語に限定する。`参` / `拾` を含む表記がユーザー辞書にだけ登録されている場合は救済されないことを、既知の制限として残す。後から加える場合は、`lookup_user` の呼び出しごとのファイル確認が照合の用途に合わないので、引き方を別に設計する
- **学習履歴**: 対象外（読み全体をキーにしていて、部分文字列の照合に使えない）

#### 3. 検索と列挙の再利用

変換 1 回（`convert_with_digit_protection` 1 回）の中で、かな run の読みと、run ごとの候補の文字列は、すべての連結候補に共通する。これを使って、準備の処理を 3 段に分ける。照合表と出力位置の照合は、**必要になった時点で作る**（改訂。当初は「run の候補に `参` / `拾` があれば作る」としていたが、それでは現行の判定で通る候補や、切り詰めで使われない候補のためにも準備が走る）。

**準備を始める条件**: 切り詰め後の連結候補を 1 件ずつ見て、(a) 現行の判定で拒否され、かつ (b) 連結後のトークン列に除外の対象がある候補についてだけ、その候補が使う run（対象を含むかな run）と run 内の候補の準備を行う。変換 1 回の中で初めて必要になったときに作り、以降の候補では再利用する。変換をまたいでは保持しない（判断済み）。

| 段 | 作る時点と単位 | 内容 | 候補数との関係 |
|---|---|---|---|
| (1) 照合表 | かな run ごとに、その run を必要とする最初の候補の判定時に 1 回 | 読みの部分文字列をすべて引き（同じ文字列は変換 1 回の中で 1 回だけ引いて使い回す）、「表記 2 文字以上で `参` / `拾` を含む」組 `(ri, rj, 表記)` を集める。出現位置 (ri, rj) は同じ文字列でも別に持つ。「対象の文字 → (組, 表記内の位置 q) の一覧」の索引にしておく | 必要な run の数に比例。連結候補数には比例しない |
| (2) 出力位置の照合 | (run, run 内の候補) ごとに、それを必要とする最初の連結候補の判定時に 1 回 | その候補文字列の中の `参` / `拾` の位置 p ごとに、索引から同じ文字の組だけを見て、`候補[p - q ..]` が表記と一致するかを確かめる。見つかった組を候補文字列内の位置で持つ | 必要になった run 内の候補の数（変換器の出力件数以下）に比例。連結候補数には比例しない |
| (3) 判定 | 連結候補ごと（上記の (a)(b) を満たすものだけ） | 生成元の区間で (2) の結果を連結候補内の位置にずらし、対象ごとの対応候補を作って、1 の流れで判定する | (a)(b) を満たす連結候補数（`num_candidates` 以下）に比例 |

- 模擬実装で N = 40 の準備に 7.1〜7.4 ms かかったのは、候補ごとに「全部分文字列 × 表記 × 出力の全位置」を調べていたため。上の分け方では、(1) は必要な run ごとに変換 1 回に 1 回、(2) は対象の位置から逆に照合するので「対象の数 × その文字を含む組の数」で済む見込み（※未計測）
- **7.1〜7.4 ms を候補数倍する構造は、この分け方で避けられる見込み**。ただし (1) の辞書検索そのもの（かな run の長さ n に対して n(n+1)/2 個の部分文字列、同じ文字列は 1 回）は、必要になった変換では 1 回走るので、ライブ変換で打鍵ごとに走る場合の負荷を計測で確かめる
- 現行の判定で全候補が通る変換、除外の対象を含む候補が無い変換では、辞書を 1 回も引かない。ただし、対象の有無を調べるためのトークン列の作成と、生成元の区間の保持は、すべての混在経路の変換で走る（4 の計測対象に含める）

#### 4. 性能の確認条件

**計測点（debug ログ、または計測用の一時テストで取得）**

| 計測点 | 取る値 |
|---|---|
| (0) 生成元の保持と数字の走査 | `combine_runs_with_origin` の区間情報の生成・複製、`scan_numeric_tokens` のトークン列の確保と走査、対象の有無の判定。対象の無い候補・現行の判定で通る候補も含む、すべての混在経路の変換で計測する |
| (1) 照合表の作成 | 作った run の数、部分文字列の数、実際に引いた回数、組の数、時間 |
| (2) 出力位置の照合 | 照合した run 内の候補の数、見つかった組の数、時間 |
| (3) 判定 | 動的計画法にかけた連結候補の数、状態数、遷移数、時間 |
| 変換 1 回の追加分 | (0)〜(3) の合計時間と、同時に使う最大のメモリ量。メモリは要素数 × 大きさに加え、確保先（`String`、`Vec<PartRef>`、`Vec<NumericToken>`、`HashMap` の辞書検索結果、照合表の索引、組の `Vec`、動的計画法の状態の `HashSet`）ごとに見積もる |

**比較の方法**

- 現行版（この変更を入れる前のコミット）と変更版で、同じ入力・同じ run の候補（合成入力では同じ `run_candidates`、実モデルでは同じ読み・同じ設定）・同じ候補数・同じ環境（同じマシン、同じビルドプロファイル）で、それぞれ複数回（例: 各 100 回以上）測る
- 所要時間は中央値、上位側（p90 / p99）、最大値を記録する。変換器の時間に対する割合だけでなく、ライブ変換に加わる**絶対時間**でも判断する
- 比較する経路
  - 混在経路で、対象の無い候補だけの変換（(0) だけが走る）
  - 混在経路で、現行の判定で全候補が通る変換
  - 混在経路で、対象を含み現行で拒否される候補がある変換（(0)〜(3) が走る）
  - 全部リテラルの経路（既存 `combine_runs` のラッパー経由。区間情報を作って捨てる分の負荷）
  - 全部かなの経路（変更の影響が無いことの確認）

**計測する場面**

- A. 変換器を使わない合成入力: `run_candidates` を直接与える関数（変換器を呼ぶ部分と、連結・検証の部分を分ける）で、#53 の読み、既存の 50 組、繰り返し語 N = 10 / 20 / 40（通す・拒否）、run の候補数 5 / 19 / 30
- B. 実モデルでの変換: 既存の `#[ignore]` 付きの診断テストと同じ形で、`2まいめをさんこうにする` など #53 の読みと、対象を含まない一般的な読み
- C. 実機: インストールした版で `rakukan-engine-dll.log` の計測ログを見る。ライブ変換（打鍵ごとの `bg_start`）と Space 変換（同期経路）の両方

**判断の基準（数値は比較計測を見て決める。実装の受入れとは分ける）**

- 目標: 対象を含まない変換では、追加時間が計測誤差の範囲であること（目標であり、達成済みとは扱わない。(0) の負荷があるので計測で確かめる）
- 対象を含む変換 1 回の追加時間を、変換器の時間に対する割合と、ライブ変換に加わる絶対時間の両方で評価する
- メモリの追加は、変換 1 回で解放される一時的なものに限る（照合表を変換をまたいで保持しない。判断済み）

#### 5. テストの設計

- `scan_numeric_tokens` 導入後も、既存の digits テストがすべて通ること（`extract_digits` の結果を変えない）

- 全探索との照合: 全探索をテスト専用のコードとして残し、小さい入力の網羅（今回と同じ組み立て）で動的計画法と一致すること
- 実辞書での確認: `#[ignore]` 付きのテストで、インストール済み辞書を使って 50 組と繰り返し語を確認する（通常の `cargo test` では実行しない）

  - 既存の完了結果の再利用: 辞書の注入前に `Done` になった同じ読みの結果は、`take_ready` で辞書なしの判定のまま返ること（初回の制限として受け入れる挙動）を、実モデルの `#[ignore]` テストで固定する。通常の `cargo test` では実行されないので、PR では実行結果を添える

#### 判断（2026-09-17、設計の確認後）

- **この設計を初回実装の土台にする**。ただし、性能評価に漏れる処理（(0) 生成元の保持と数字の走査）と、照合表を作る時点（必要になった時点）は、依頼前に設計へ反映する（反映済み）
- 性能の数値は、比較計測を見て決める。実装の受入れとは分ける。現行版との差を、同じ入力・候補数・環境で複数回測り、中央値・上位側・最大値を確認する。変換器に対する割合だけでなく、ライブ変換に加わる絶対時間でも判断する。「対象なしは計測誤差内」は目標で、達成済みとは扱わない
- 照合表は、初回は変換をまたいで保持しない。変換 1 回の中で再利用する範囲にとどめ、保持期間や辞書の更新への対応を増やす前に、この構造での負荷を確認する
- ユーザー辞書は初回の根拠に含めない。学習履歴も対象外
- 無効化の設定は、初回は設けない。性能や判定に未解決の問題があれば受入れ前に解消する。設定が無いことを理由に、問題を残して採用することはしない
- 実装は、従来の方針どおり nick に PR を依頼する方向で進める。まず依頼文を確認する段階とし、投稿はまだ行わない
- 辞書の注入前に完了した同じ読みの結果が残る扱いは、初回の制限として受け入れる。辞書なし・注入後の新しい要求・既存の完了結果の再利用を、それぞれテストで固定する

#### 既知の制限（初回）

- 通常の漢数字は除外の対象外: `2まいとさんまい` → `2枚と三枚`、`2ばんとじゅうばん` → `2番と十番` は拒否のまま
- 辞書に表記が無い数詞は救済されない: `2まいとさんまい` → `2枚と参枚`（`参枚` のエントリが無い）
- 大字と通常の漢数字で結果が異なる: `2番と拾番` は通り、`2番と十番` は拒否
- ユーザー辞書の登録語は根拠にならない（登録語でしか正当化できない表記は救済されない）。学習履歴も根拠にならない
- 変換結果全体の語義・位置の正しさは保証しない: `2かいのさんかい` → `2参会の散会` は通過を許容（変換品質上の問題は残る）
- 辞書の注入前に `Done` になった同じ読みの結果は、再変換されるまで辞書なしの判定のまま
- 対象文字は `参` / `拾` だけ（`壱` / `弐` は対象外）

#### #57 監視の開始・終了・再利用（経路ごと）

**監視の仕組み**: `bg_timeout_watchdog(is_stuck)` は TSF プロセスごとの `Mutex<Option<Instant>>` を `try_lock` で扱う。`true` で「未記録なら今の時刻を記録し、記録から 20 秒以上なら `engine_reload_force()`」、`false` で「記録を消す」。ロックが取れないと、記録も消去も何もせず抜ける。

**整理**

- 報告の主経路（Space が 250 ms を超える → `on_waiting_timer` で候補を出す → 記録が残る → 後の遅い Space で古い時刻から数えて再起動）は、コードと合う
- 待機タイマーの上限（10 秒）は監視の閾値（20 秒）より短い。1 回の待機の中では監視が発火する前に待機が終わるので、**本当に応答が返らない場合の検出は、記録を次の待機まで残すことで成り立っている**（詰まったまま待機が終わり、次の Space でも `running` なら、残った時刻から数えて再起動する）。したがって「待機が終わったら消す」では受入条件 4 を満たさない（※当初「消してよいのは完了を観測したときだけ」と書いたが限定しすぎだった。監視している実行やエンジンが置き換わった場合も測り直す対象で、判断後の設計では「同じ実行かどうか」で維持と測り直しを決める。9 節「#56 / #57 の設計」）
- **`false` を数か所足す案（`e8eeac9`）で足りるか**: 足りない見込み
  - 受入条件 1: 選択中のキー操作の経路（`dispatch.rs:198-233`）や Space の取り出し経路など、完了を観測して消さない場所が残る
  - 受入条件 2: 完了を観測しないまま待機が終わり（取り消し・非アクティブ化など）、その後に変換が終わると、次の変換で古い時刻が使われうる。`e8eeac9` は「ワーカーが idle のまま `bg_start` する時点」で消すが、前の結果が `done` のまま残っている場合は idle にならない（※推測。経路の実測はしていない）
  - 受入条件 3: `try_lock` に失敗すると消去が黙って飛ばされる点は変わらない
- **設計の方向（案、未検証）**
  - 完了の観測を 1 か所に集める: TSF 側で、`bg_status` の取得・候補の取り出し・変換の開始を通す小さな関数を用意し、「`running` 以外を観測した」「候補を取り出せた」で必ず消し、「完了を観測した後に新しい変換を始めた」で開始時刻を付け直す。監視の状態は、ロックを使わない原子的な値（例: 開始時刻のミリ秒、0 = 未記録）にして、消去が失敗しないようにする
  - もう 1 つの案: エンジン側（`conv_cache`）は `Running` に入った時刻を正確に知っているので、「実行中の経過時間」をエンジンから返し、TSF は記録を持たない。記録が残る問題は構造的に無くなるが、RPC の応答を変えるので `PROTOCOL_VERSION` の更新が要る
  - どちらでも、監視の状態を時計を差し替えられる形にして、経路ごとの状態遷移（完了の観測、未観測での待機終了、詰まりの継続）を単体テストで固定する

#### #56 復旧の契機

- **ホストやエンジンの世代を示す既存の情報は無い**。`Hello` の応答はプロトコルの版だけで、プロトコル・ホスト（`server.rs`）・クライアント（`client.rs`）に PID・インスタンス ID・世代番号の類は無い。再接続は `call_with_retry` の中で行われ、呼び出し元には知らされない
- **同じホスト内でもエンジンは作り直される**: `Create` の設定がホストの保持値と違うと `load_engine_into` で作り直す（別の TSF プロセスからの `Create` でも起きる）。このときも読みバッファは空になり、TSF には知らされない
- **RPC の失敗と「空」を区別できない**: `preedit_is_empty()` は失敗時に `true`（`unwrap_or(true)`）、`hiragana_text()` は空文字列を返す。`e8eeac9` の判定（読みが空かつ composition が生きている）は、ホストが落ちている間も成り立ち、打鍵ごとに復元と WARN が走る
- **共有エンジン**: ホストのエンジンは全アプリの TSF 接続で共有する 1 つ（`SharedEngine`）。`OnKillThreadFocus` は候補ウィンドウとタイマーを止めるだけで、composition の確定・取り消しやエンジンのリセットはしない。そのため「composition が生きていてエンジンの読みが空」は、別アプリで入力して確定した後にも起こりうる。逆に、別アプリの読みが共有バッファに残っていれば、読みは空でなく、食い違いは検出されない（※推測。アプリがフォーカスを失ったときに composition をどう扱うかはアプリによるので、実機で確認が要る）
- **必要になりそうな情報（案）**: RPC の成功・失敗を区別して返す取得関数、エンジンの世代（ホストがエンジンを作るたびに変わる値）を TSF が composition の開始時に覚え、変化で入れ替わりを判定する仕組み（プロトコルの変更が要る）。共有バッファを別アプリが使った場合の扱いは、別の設計課題

### 2026-09-17 #56 / #57 の設計（案）

#### 判断

- **#57**: 監視する対象を「同じ実行中の変換」に改める。設計の軸は B（エンジン側で実行を識別し、その実行の開始からの経過時間を返す）。A（TSF 側で観測を集約、原子的な値）は、観測していない間に「前の変換が完了し、別の変換が始まった」ことを区別できない問題が残るので採らない。当初の受入条件「次の待機では開始時点から測る」は、同じ変換が詰まったまま待機画面だけ終わった場合に監視時間を引き継げないので不十分だった
- **#56**: エンジンの世代情報を追加する方向で進める。ただし、世代だけでは復旧条件は完成しない
- どちらも、今は設計と nick への返信の下書きまで。PR は分ける。共通するプロトコル・ABI の変更の順序は nick にも相談する

#### 前提（コードで確認した事実）

- **状態取得の経路**: TSF `RpcEngine::bg_status`（`BgStatus` 要求。失敗時は空文字列）→ ホスト `dispatch_engine` → `DynEngine::bg_status`（`rakukan-engine-abi`）→ エンジン DLL の `engine_bg_status`（`ffi.rs`。ハンドルを受け取るが、中では DLL 全体で 1 つの `conv_cache::status()` を読む）→ `"idle"` / `"running"` / `"done"` / `"error"`。`conv_cache` の `State::Running` は読みのキーだけを持ち、実行の識別子や開始時刻は持たない
- **ABI**: `EngineVTable::load` は `engine_abi_version` の完全一致を確かめ、必須のシンボルを `load_sym!` で読む。関数を足すと、DLL 側の `ENGINE_ABI_VERSION`（`ffi.rs`）と ABI 側の `EXPECTED_ENGINE_ABI_VERSION`（`rakukan-engine-abi`）の両方の更新が要る
- **DLL の寿命**: `DynEngine` は `Arc<Library>` を持ち、落とすと参照が減る。ホストは `Create` の設定が違うとエンジンを作り直す（`load_engine_into`）
- **ホストの周期処理**: 無い。健全性の判断（#43）は、要求を処理した後に `apply_health_action` で `bg_status` を 1 件観測して行う。自己終了は、応答を書いた後に `exit_after_response` を見て行う。`EngineHealth` 要求は、変換中でもエンジンのロックを取らずに応答する
- **ホストのエンジンは全接続で共有する 1 つ**（`SharedEngine`）。`OnKillThreadFocus` は composition もエンジンの読みも触らない
- **世代・インスタンスの識別子は無い**。`Hello` はプロトコルの版だけを返す。`Create` の応答は `Unit`
- **再送**: `call_with_retry_inner` は、書き込み失敗でも読み込み失敗でも再接続して同じ要求を最大 2 回送る。読み込みの失敗は「ホストが適用して応答した後に接続が切れた」場合も含むので、読みを変える要求（`InputChar`、`Backspace`、`ForcePreedit`、`Commit` など）が二重に適用されうる
- **取得関数の失敗時の値**: `preedit_is_empty()` は `true`、`hiragana_text()` は空文字列、`bg_status()` は空文字列（TSF 側では `running` 以外として扱われる箇所がある）

#### #57 の設計（案）

**1. エンジン側で実行を識別する**

- `conv_cache` の実行ごとに、単調に増える実行番号（DLL を読み込んでいる間、ワーカーが `pending` を取り出すたびに 1 増やす）と、`Running` に入った時刻を持つ。`Done` にも、どの実行の結果かを残す
- 新しい FFI 関数（例: `engine_bg_run_info`）で「実行番号、状態、`Running` なら開始からの経過ミリ秒」を返す。`conv_cache` は DLL 全体で 1 つなので、エンジンのハンドルやホストのエンジンのロックに依存しない形にする
- **ABI の変更が要る**: FFI 関数の追加、`EngineVTable` への追加、ABI の版を 2 か所で上げる。ホストと DLL は同じビルドで揃える必要がある（既存の版の検査で、揃っていなければ読み込みを拒否する）

**2. 監視はホストが行う（推奨）**

- ホストに監視用のスレッドを 1 本置き、一定間隔（例: 1〜2 秒）で上の関数を呼ぶ。同じ実行番号が閾値を超えて `Running` のままなら、ホストを自己終了する（#43 の自己終了と同じく、マーカーの試行回数に数えるかは要設計）。TSF は再接続で新しいホストを起動する
- **いつ誰が監視するか**: ホストが、UI の状態や TSF の操作と無関係に、実行中の間ずっと監視する。10 秒で待機タイマーが終わった後も監視は続く
- **UI の待機の終了と変換の終了の区別**: 監視は変換の実行だけを見るので、待機画面の終了（上限、Esc、非アクティブ化）は影響しない
- **同じ実行なら維持、新しい実行なら測り直す**: 実行番号が変われば別の実行として測り直す
- **状態取得の失敗を完了と扱わない**: ホスト内の関数呼び出しなので RPC の失敗は関与しない。関数が状態を返せない場合（`conv_cache` のロックの毒化など）は「不明」とし、完了にも詰まりにも数えない
- **古い応答で別の実行や回復したエンジンを再起動しない**: 終了を決める直前に同じ関数で実行番号と状態を取り直し、同じ実行番号がまだ `Running` のときだけ終了する。判断する主体がホスト 1 つなので、複数の TSF プロセスが古い観測で再起動を重ねることも無い
- **TSF 側**: `bg_timeout_watchdog` と `engine_reload_force()` の自動起動を取り除く（言語バーの「エンジン再起動」は残す）。TSF の UI 側で `bg_status` を読む箇所は、取得に失敗した値（空文字列）を `done` / `idle` と同じに扱わないよう確認する
- **閾値**: エンジン側の生成の上限（`GEN_TIMEOUT_SECS` = 15 秒）より長くする。現行の 20 秒を引き継ぐかは要判断。文書の「30 秒」の記述は、決めた値に揃える
- **RPC の変更**: 監視をホストの中で完結させるなら、RPC の要求・応答の追加は不要の見込み（`PROTOCOL_VERSION` は変えない）。TSF で実行番号や経過時間を表示・記録したい場合だけ追加する

**3. 確認・設計が要る点**

- **DLL の寿命と監視スレッド**: 監視スレッドが DLL の関数ポインタを使う間、DLL がアンロードされないこと。`Create` でエンジンを作り直すときの `Arc<Library>` の扱い（監視側も参照を持つか、作り直しの間は監視を止めるか）
- **ホストのエンジンのロックとの関係**: 監視は `SharedEngine` のロックを取らない形にする（変換中はロックが長く保持される）。`conv_cache` のロックは短時間
- **エンジン DLL 内のスレッドの制約**: 監視スレッドはホスト（exe）側に置き、DLL 内には新しいスレッドを作らない（既存の方針「エンジン DLL 内で BG スレッドや Drop の I/O をしない」）
- **#43 の健全性との関係**: 推論失敗の連続（#43）と、実行の詰まり（#57）の自己終了を、同じマーカー・試行回数で数えるか
- **テスト**: 実行番号と経過時間の遷移（開始・完了・失敗・次の実行）、監視の判断（同じ実行の継続、別の実行、取り直しで回復していた場合、状態不明）を、時計を差し替えられる形で単体テストにする

**代案（採らない理由）**: TSF が実行番号付きの条件付き再起動要求（例: 「実行番号 R がまだ実行中なら再起動」）を送る形もあるが、TSF が監視する契機（キー操作や待機タイマー）が無い間は検出されず、複数の TSF プロセスからの要求の調停も要る。

#### #56 の設計（案）

**1. 世代**

- ホストがエンジンを作るたびに新しい世代を割り当てる（`load_engine_into`）。世代は「ホストのインスタンスの識別子（プロセス ID と起動時刻など、再起動の前後で重ならない値）」と「そのホスト内の作成回数」の組にし、ホストの再起動でも、同じホスト内の作り直しでも変わり、再起動の前後で同じ値にならないようにする（乱数の crate は現在の依存に無いので、既存の依存だけで作れる値を選ぶ）
- 世代は `Create` などの応答と、読みを変える要求の応答で TSF に返す

**2. 共有エンジンの使用者（所有者）**

- 共有エンジンの読みを、どの composition のものとして持っているかをホストで記録する（所有者 = TSF プロセスと、そのプロセス内の composition の識別子）
- 所有者は、composition を始める要求で設定し、確定・取り消しで解除する
- 別の所有者の読みがある状態で、所有者でない composition から読みを変える要求が来た場合の扱いを決める（その composition 用に読みを入れ替えるか、拒否して TSF に復元を求めるか）。**別アプリの読みを黙って上書きしない**ことを条件にする

**3. 検出と適用の順序（打鍵を新しいエンジンへ適用してから気付かない）**

- 読みを変える要求に「期待する世代」と「所有者」を付ける。ホストはエンジンのロックを取った中で、世代と所有者を確かめてから適用する。合わなければ適用せず、「世代違い」「所有者違い」と現在の世代を返す
- TSF は「世代違い / 所有者違い」を受けたら、復元の要求（下記）を送り、その応答で新しい世代を受け取ってから、元の操作を送り直す
- この形なら、ふだんの打鍵で確認用の RPC を増やさない（毎打鍵の追加 RPC を無くす）。WARN は、世代違い・所有者違いを検出して復元した 1 回ごとに 1 行にする

**4. RPC の再送による二重適用**

- 読みを変える要求は、`call_with_retry_inner` の自動再送の対象から外すか、要求番号（所有者ごとの連番）を付けてホストが同じ番号を 2 回適用しないようにする。どちらにするかは要設計
- 再接続で新しいホストに送り直された場合は、世代違いで拒否されるので二重適用にならない。同じホストで接続だけが切れた場合が、要求番号などで防ぐ対象

**5. RPC の失敗と「空」の区別**

- TSF で使う取得関数（`preedit_is_empty`、`hiragana_text`、`bg_status` など）は、失敗を値に潰さず、失敗として返す形にする。失敗は復元の契機にしない

**6. 復元元の編集状態の保持場所**

- エンジンの状態は失われうるので、復元元は TSF 側に置く。composition ごとに、直近に確定したエンジンの編集状態（少なくとも読み。表示文字列とは分ける）を、読みを変える要求の応答（`InputCharResult` の `preedit` / `hiragana` など）から更新して持つ
- 現状、通常の入力ではセッションが `Idle` のままなので、セッションの状態とは別に持つ必要がある
- **未確定ローマ字や打鍵履歴を含む復元は未確定**。まず読みだけを戻す場合の、`たt` の表示、復元後の Backspace・Space・次の文字入力の挙動を、実機かテストで確かめてから範囲を決める

**7. 変更範囲**

- プロトコル: 世代・所有者・要求番号（採る場合）・世代違いの応答・復元の要求を追加する。`PROTOCOL_VERSION` を上げる（TSF とホストの版が揃うまで接続できない。更新はサインアウト / サインイン）
- ABI: 世代と所有者はホスト側で管理するので、エンジン DLL の ABI の変更は不要の見込み（復元の要求で未確定ローマ字まで戻す場合は、エンジンの関数の追加が要りうる）
- TSF: composition ごとの編集状態の保持、世代違い・所有者違いの処理、取得関数の失敗の扱い
