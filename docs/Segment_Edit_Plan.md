# 課題: 範囲指定変換の文節編集モード化（Left / Right での変換対象移動）

作成: 2026-09-07

位置づけ: 2026-09-07 の検討で洗い出した論点と推奨案を、着手時の出発点として記録する。決定事項ではない

関連 Issue: #32（問題点の記録。統合ブランチ側の自動分割案は #18 の A を参照）、#16（`DictLookup` の転用可能性）

## 1. 背景

README の「範囲指定変換: Shift+Right/Left で先頭から変換範囲を指定 → Space で変換 → Enter で確定、残りで LiveConv 再開」は実装されており、ログ上も動作している。ただし次の 2 点が問題になった。

- 範囲の表示が下線の種類（選択範囲＝実線、残り＝点線）だけで、下線を描画しないアプリでは何も起きていないように見える
  → 2026-09-07 の `6c8a2fe` で、範囲指定中はキャレットを選択範囲の末尾に置くよう修正済み
  → ただし入力先によってはキャレットも判別できない（実機で確認）。追加の改善案は 6. を参照
- 範囲指定中に Left / Right で変換対象を移動できない。「、」区切り変換（BlockSelecting）と同じように、文節間をフォーカス移動したい
  → 本課題

## 2. 現状の仕組み

- RangeSelect（`engine/state.rs`）は「先頭からの境界 1 つ（`select_end`）」しか持たない。文節の一覧という概念がなく、Left / Right は消費するだけで何もしない（`edit_ops.rs` の `on_block_focus_move` が BlockSelecting 以外では no-op）
- Space を押すと選択部分を engine の preedit に入れ替えて通常変換フロー（Selecting）へ移り、残りは remainder 文字列として持ち回る。Enter で候補を確定すると remainder が次の preedit / LiveConv になる
- BlockSelecting は、突入時に全ブロックを同期変換済みで、各ブロック（`ConversionBlock`）が読み・候補一覧・選択番号・末尾の句読点を持つ。Left / Right はフォーカス移動、Space は現在ブロックの候補送り、Enter は全ブロック一括確定

## 3. 洗い出した問題点

1. **データモデルが足りない**。移動先が存在するには「文節の一覧 + 現在位置」が必要。RangeSelect は境界が確定していないので、BlockSelecting のような突入時の一括変換ができない
2. **境界を動かしたときの隣接文節の扱い**。現在文節を 1 文字伸ばしたら次の文節が 1 文字縮む（MS-IME 方式）のか、後続の境界をまとめてずらすのか。次の文節が 0 文字になったら消すのか。文節の最小長は 1 文字とするか
3. **Space の意味が現状と衝突する**。今は Space で Selecting に遷移して文節構造が消える。移動後も各文節の選択候補を保持するには、Space は「その場で候補を出す」BlockSelecting 型に変える必要がある。`on_convert.rs` の RangeSelect → Space 経路（inline 待機 + WM_TIMER フォールバック、モデル未ロード時の分岐）を書き直すことになる
4. **Enter の意味が変わる**。今は「選択部分だけ確定して残りで LiveConv 再開」。フォーカスが動かせると「どこまで確定するか」が曖昧になる
5. **未変換の文節をどう確定するか**。Space を押していない文節を、ひらがなのまま確定するか、確定時に自動変換するか、フォーカスが離れた時点で変換するか。自動変換にすると文節移動のたびに変換待ち（LLM の場合 250 ms 以上）が入る
6. **候補ウィンドウの扱い**。未変換文節へ移動したときは候補がないので閉じるのか、その場で変換して出すのか
7. **Home / End の意味**。今は RangeSelect で「境界を先頭 / 末尾へ」。文節モデルでは「先頭 / 末尾の文節へフォーカス移動」の方が自然。BlockSelecting の Home / End は未定
8. **ESC / Backspace / 文字入力の扱い**。RangeSelect は全部キャンセルしてひらがなに戻し、BlockSelecting の文字入力は現状を確定してから入力する。統合するならどちらかに揃える
9. **学習と文脈**。Selecting と BlockSelecting は別々の確定経路で自動学習している。新しい確定経路にも学習を入れる必要がある
10. **「、」を含む文との関係**。選択範囲に「、」が含まれる場合の現行挙動は未確認（RangeSelect の Space 分岐は句読点分割より先に評価される）。2 つの分割方式が並存している
11. **キャレット位置**。「選択範囲末尾にキャレット」は文節モデルでは「フォーカス文節の末尾」になる。共用描画関数 `update_composition_parts_impl`（`on_compose.rs`）に prefix 付きでキャレット位置を指定できる小さな拡張が要る

## 4. 推奨案: RangeSelect を BlockSelecting に統合し、Shift+矢印で境界を編集する

上の 1・3・4・6・10 をまとめて解消する。以下はすべて提案で、未実装。

### 4.1 モデル: 文節列 + フォーカス

状態は BlockSelecting の既存構造（`ConversionBlock` の配列 + `current_index` + 元の全体読み）をそのまま使う。

- **突入時の初期分割**。「、」「。」を含む文は今と同じく句読点で分割する。含まない文は「全体で 1 文節」とする。Shift+Right / Left の入口も、Space での句読点分割の入口も、同じ状態に入る
- **未変換文節**。候補一覧が空の文節は「未変換」で、表示も確定も読みのまま
- **RangeSelect の入口の再定義**。LiveConv や Preedit で Shift+Right を押したときは「全体 1 文節、未変換」で突入し、そのまま Shift+Right を 1 回分（先頭 1 文字）適用する。Shift+Left なら「末尾 1 文字を切り離した状態」になる。どちらも現状の見た目と一致する

### 4.2 キー操作と遷移

**Shift+Right / Shift+Left（境界編集）**。現在文節の右端を 1 文字動かす。MS-IME と同じ「隣と文字をやり取りする」ルール。

- 伸ばす: 次の文節の先頭 1 文字を現在文節の末尾に移す。次の文節が空になったら削除。末尾文節では何もしない
- 縮める: 現在文節の末尾 1 文字を次の文節の先頭に移す。次の文節が無ければ新しく作る。現在文節は最小 1 文字
- 境界を動かした文節（と隣の文節）は候補を捨てて「未変換」に戻す
- 句読点は文節の末尾属性なので、境界編集は句読点をまたげない、と単純化する。またぐ操作が必要かは実機で判断

**Left / Right（フォーカス移動）**。`on_block_focus_move` をそのまま使う。端では消費して何もしない。移動先が未変換なら候補ウィンドウを閉じ、変換済みならその文節の候補を表示する。

**Space（変換）**。現在文節が未変換なら、その読みを変換して候補一覧を持たせ、先頭候補を表示する。変換済みなら次候補へ送る。変換はブロック突入時と同じ同期変換（`engine_convert_sync_multi`）で揃える。RangeSelect の「inline 待機 + WM_TIMER フォールバック」経路は使わない（Selecting へ抜けると文節構造が失われ、Left / Right で戻れなくなるため）。

**Enter（確定）**。全文節を先頭から連結して一括確定する。変換済み文節は選択候補、未変換文節は読みのまま。RangeSelect の「選択部分だけ確定して残りで LiveConv 再開」は廃止する（README と `DESIGN.md` の記述変更を伴う）。部分確定が必要になれば、別キーで「現在文節までを確定」を後から足す。

**Home / End**。「先頭文節 / 末尾文節へフォーカス移動」に統一する。

**ESC / Backspace**。BlockSelecting の現行どおり、全文節を解除して元の全体読みをひらがなの Preedit に戻す。RangeSelect の「元の LiveConv プレビューを復元する」動作は、Preedit に戻った時点でライブ変換タイマーが再度走れば実質同じ結果になる（※ タイマーが Preedit 復帰で再武装されるかは実機確認が必要）。

**文字入力**。BlockSelecting の現行「現状を確定してから入力」に揃える。途中まで文節を組んだ状態の取り消しは ESC で行う。

### 4.3 表示・確定後処理

- **表示**。共用描画関数の (prefix, converted, suffix) をそのまま使う。prefix はフォーカスより前の文節、converted はフォーカス文節、suffix は後ろの文節。属性はフォーカス文節が実線、他は点線。キャレットは converted の末尾（prefix が空でない場合への拡張が必要）
- **学習**。BlockSelecting は今、全体読みと全体テキストの 1 組で学習している。統合後は文節ごとに「読み → 選択候補」を学習させる。未変換文節や読みと候補が同じ文節は対象外
- **文脈**。確定テキストは今と同じ経路で `engine.commit` に渡るので変わらない

### 4.4 変更対象（主なもの）

- `engine/state.rs`: RangeSelect variant を削除し、BlockSelecting に境界編集メソッド（伸縮・未変換化）を追加
- `tsf/factory/edit_ops.rs`: `on_segment_extend` / `on_segment_shrink` を BlockSelecting 向けに書き直し、`on_cursor_jump` を文節移動へ変更
- `tsf/factory/on_convert.rs`: RangeSelect の Space / Enter / ESC / Backspace 分岐を削除し、Space に「未変換文節の変換」を追加
- `tsf/factory/on_input.rs`: RangeSelect の入力キャンセル分岐を削除
- `tsf/factory/on_compose.rs`: キャレット配置を prefix 付きに拡張
- `README.md` / `docs/DESIGN.md` / `docs/handoff.md`: 範囲指定変換の説明を文節編集として書き直し

### 4.5 残るリスク

- 同期変換は LLM を使うと文節ごとに待ちが入る。突入時に全文節を変換する現行 BlockSelecting でも同じ待ちが発生しているので体感は変わらない見込みだが、境界を頻繁に動かすと再変換が増える
- 今の RangeSelect には「モデル未ロード時は読みをそのまま候補にする」分岐がある。同期変換側にも同等の扱いがあるかは未確認

## 5. 着手前に決めること

1. 境界編集のルール: 隣と文字をやり取りする案（4.2）でよいか
2. Enter の範囲: 全体一括確定でよいか。部分確定（残りで LiveConv 再開）を残すか
3. 未変換文節の確定: 読みのままでよいか、確定時に自動変換するか
4. ESC と文字入力の扱い: BlockSelecting に揃えてよいか

## 6. 課題: 範囲の可視化が入力先に依存する

### 6.1 現状

範囲指定中の表示は、次の 2 つに頼っている。どちらも最終的にアプリが描くため、アプリが無視すると何も見えない。

| 手段 | 実装 | 見えない条件 |
|---|---|---|
| 表示属性の下線 | `globals.rs` の 2 属性。選択範囲＝実線（`TF_ATTR_TARGET_CONVERTED`）、残り＝点線（`TF_ATTR_INPUT`）。文字色・背景色は `TF_CT_NONE` | 表示属性を描画しないアプリ。高 DPI やダークテーマで点線と実線の差が判別できない場合 |
| キャレット位置 | `6c8a2fe`。`update_composition_parts_impl`（`on_compose.rs`）で選択範囲末尾に Collapse | composition 内のキャレット位置を無視して末尾に描くアプリ、変換中にキャレットを出さないアプリ（※ 具体的にどのアプリかは未整理。実機で「判別できない入力先がある」ことは確認済み） |

### 6.2 改善案

**案 A: 自前のウィンドウで範囲を表示する（確実）**

候補ウィンドウ（`candidate_window.rs`）と同じ仕組みで、範囲指定中だけ小さなウィンドウを出し、「選択範囲｜残り」を色分けして表示する。描画を rakukan が持つので入力先に依存しない。

- 位置は候補ウィンドウと同じ `caret_rect`（`GetTextExt` の結果）を使う。`update_composition_parts_impl` は範囲指定の経路でも composition 全体の矩形を取れる
- 表示内容は 1 行。選択範囲を反転または太字、残りを通常色で描き、末尾に「Shift+←→ で範囲 / Space で変換」程度の操作ガイドを付けられる
- 候補ウィンドウの `show_with_status` は候補一覧が前提（空なら `hide`）なので、そのまま流用はできない。1 行表示用の描画モードを足すか、別の小さなウィンドウにする
- 範囲指定を抜けたら閉じる（Space → 候補ウィンドウに置き換わる、Enter / ESC / Backspace → hide）
- 文節編集モード（4.）に統合した後も、フォーカス文節の表示として同じウィンドウを使える
- 作業量: 中。描画・レイアウト・ライフサイクル（hide 漏れ）の実機確認が要る

**案 B: 実際のテキスト選択（反転表示）にする（安価だが要検証）**

`TF_SELECTION` を collapse せず、先頭から `select_end` までの非空範囲にする。通常のエディタで Shift+Right した時と同じ反転表示になり、選択の描画はほぼ全アプリが持つ。

- 変更は `update_composition_parts_impl` の Step3 だけ
- リスク: composition 内に非空選択を置いたときの挙動はアプリ依存。次の `SetText` や確定で選択部分が置換・削除される、IME 側の選択変更をアプリが「ユーザー選択」として扱い別の処理を起動する、などが考えられる（※ 推測。実機確認が必要）
- 試す価値はある。案 A の前に 1〜2 のアプリで挙動を見て、問題があれば捨てる

**案 C: 表示属性に文字色・背景色を付ける（補助）**

選択範囲の属性の `crBk` / `crText` を `TF_CT_SYSCOLOR`（`COLOR_HIGHLIGHT` / `COLOR_HIGHLIGHTTEXT`）にする。MS-IME の注目文節と同じ見た目。

- 変更は `globals.rs` の定数だけ
- 表示属性を描画するアプリでは下線の有無に関係なく判別できるが、描画しないアプリには効かない。単独では今回の問題を解決しない
- 案 A と併用すると、対応アプリでは本文側にも範囲が出る

**案 D: 確定単位を小さくして範囲指定の必要を減らす（設計側）**

範囲指定が必要になる場面（ライブ変換の文節切りが違う）を、文節編集モード（4.）の Left / Right 移動と候補選び直しで吸収し、範囲の視認性そのものへの依存を下げる。案 A〜C の代替ではなく、4. の実装後に効く話。

### 6.3 推奨

- **案 A を本命**にする。入力先に依存しない唯一の手段で、文節編集モードにもそのまま使える
- 着手前に**案 B を短時間で試す**。数行の変更で済み、問題なく動くアプリでは案 A の補助になる。問題が出れば即座に戻す
- 案 C は案 A と同時に入れる（定数変更のみ）
- 案 D は 4. の一部として扱う

### 6.4 決めること

1. 案 A のウィンドウを候補ウィンドウの表示モードとして足すか、別ウィンドウにするか
2. 案 A の表示内容に操作ガイドを含めるか
3. 案 B を試す対象アプリ（キャレットが判別できなかった入力先を含める）
