# ログの作り方の見直し（2026-10-10 起案）

状態: **設計済み・未実装**（8 章の決めごとは 2026-10-10 にすべて決定）。Issue: 段 1 #72（0.12.0）、段 2 #73、段 3 #74、段 4 #75、段 5 #76（段 2〜5 は #33 の対応の中で行う）。Codex CLI のレビュー（2026-10-10、4 回）を取り込み済み。

## 1. きっかけ

- 2026-10-10、`sudo cargo make install` の regsvr32 が 4 回続けて 0xC0000005 で失敗し、インストールが手順 3 で止まった。`register_debug.log` には `DllRegisterServer success` が出ている（登録の 3 段階は成功。関数の戻りまでは示さない）。
- cdb で取ったスタック（`C:\rb\regsvr32-cdb.log`、観測）: regsvr32 の本体が `FreeLibrary` で DLL を外している間に、`DllMain` が起動した `rakukan-log-cleanup` スレッドが外された `VCRUNTIME140.dll` を実行して落ちた。`rakukan-config-watch` スレッドは 30 秒の待ちの途中で、落ちていない。
- イベントログには、regsvr32 の同じ種類のクラッシュ（BEX64、`VCRUNTIME140.dll_unloaded`）が 9/24・10/8・10/10 午前（インストール成功時）にも出ている（観測）。終了コードが 0 になるかが落ちる時点で変わる、という説明は解釈（※推測）。
- 掃除のスレッドは TSF のログを全部数える。ファイルは 3808 個（ログ 1904 + `.lock` 1904、109.5MiB、9/19〜10/10）。256MiB を超えるまで 1 つも消えず、件数・日数の上限が無い。ファイル数が落ちやすさを上げたという説明は ※推測。
- **最優先の要件: ログの仕組みがインストーラー（regsvr32 による登録・解除）を妨げないこと。**

`DllMain` の `PROCESS_ATTACH` では、ほかに `config_save_default` / `init_config_manager` / `keymap_save_default` / `start_reload_watcher`（設定監視スレッド、本番には停止経路が無い）を行っている。

登録・解除の記録: `DllRegisterServer` は `register_debug.log` に、失敗時または最後にまとめて上書きする。`DllUnregisterServer` は tracing だけで、`unregister_server()` は各解除のエラーを捨てて常に `Ok` を返す（`crates/rakukan-tsf/src/tsf/registration.rs:184-189`）。**regsvr32 の終了コード 0 だけでは解除の成功を示さない。**

## 3. 方針

1. **`DllMain` では何も起動しない・何も作らない。** DLL のハンドルを保存するだけにする。
2. **実行時の初期化は、最初の有効な `Activate` で、DLL インスタンスにつき 1 回。** Activate されない読み込み（regsvr32 の登録・解除、Activate 前の照会）では、実行時のログ・`.lock`・スレッドを作らない。登録・解除の専用の記録（`register_debug.log` など）は例外とする。
3. **Activate した後は、DLL をプロセスが終わるまで外させない**（`GetModuleHandleEx(FROM_ADDRESS | PIN)`）。今の `DllCanUnloadNow = S_FALSE`（常駐させる設計）を、明示的な `FreeLibrary` に対しても成り立たせる。
4. **掃除は DLL の外（トレイ）で行う。** 消す条件は日数と件数を独立に持つ（容量の上限は設けない）。
5. **ファイルの 1 行目（ヘッダー）と各行で、発生元を特定できるようにする。**
6. **ホスト・engine DLL のログも同じ方針に揃える。**
7. **キー処理の経路でファイル I/O を待たない（書き込みを別スレッドへ）。ETW は調査用に併用する。**

## 4. 段階

推奨の順序: 段 1 → 段 2 → 段 3 → 段 4 → 段 5。インストールの経路で扱う事項（トレイの配布・起動、登録の成否の判定、旧版での登録解除）は、この計画に含めず #33 に回した（`docs/Installer_Redesign_Plan.md` の 4.3a）。共有 crate の名前・ファイル形式・保持規則は段 2 の前に決める。

### 段 1: `DllMain` を空にし、Activate で初期化する（インストーラーの妨げを除く）— #72、0.12.0

**DllMain**: `DLL_INSTANCE` の設定だけ。

**Activate**（`crates/rakukan-tsf/src/tsf/factory.rs:357`）: 引数の検証（`ptim=None` の拒否、`factory.rs:359`）の後、keymap の読み込み・COM の登録より前に `runtime_init_once()` を呼ぶ。

- 中身（今の `DllMain` と同じ順）: DLL の PIN → ログ（subscriber、`.lock`、`RotatingLog`）→ `config_save_default` → `init_config_manager` → `keymap_save_default` → `start_reload_watcher`。初期化した後に、今の設定の由来と revision をログに書く（subscriber より前の出来事は記録されないため）。
- `std::sync::Once` で 1 回だけ。初期化の中では、sink の登録・UI の操作・エンジンの起動をしない。設定のロックや `RefCell` の借用を持ったまま呼ばない（再入による停止を避ける）。
- 失敗しても入力は止めない。ログが作れなければログなしで続ける。`try_init()` の失敗を記録する。監視スレッドの起動に失敗したら記録し、再試行はせず、モード切替・言語バーのエンジン再起動・ホストへの再接続のときの読み直しだけで続ける（2026-10-10 決定）。
- 設定監視は、監視を登録した直後に、**監視スレッドの中で** 1 回読み直す（初期読み込みと監視開始の間の保存を逃さない）。
- 掃除のスレッドは DLL から外す（段 3 でトレイへ）。

**Activate 前の経路を副作用の無い形にする**（コードで確認済み）:

| 経路 | 今の動作 | 直し方 |
|---|---|---|
| `DllGetClassObject` → `ClassFactory::create` → `TextServiceFactory::new` | `Keymap::default()` → `keyboard_layout()` → `CONFIG_MANAGER` の初回参照で `config.toml` を読む（`factory.rs:325`、`keymap.rs:525`、`config.rs:794`） | 生成時は設定を読まない。keymap は Activate で読む |
| 言語バーのツールチップ `GetTooltipString` | エンジンが無ければ背景の初期化スレッドを起動し、ホストへの接続・起動まで進む（`factory.rs:1103-1127`、`state.rs:379-388`） | 既にあるエンジンを参照するだけにする |
| 言語バーのメニュー（オン/オフ、エンジン再起動） | Activate 前でも設定・keymap の読み直し、再起動のスレッドへ進む（`factory.rs:147-176`） | Activate 前は何もしない（※推測: Windows が Activate 前にメニューを出すかは未確認） |
| 言語バーの `GetInfo` / `GetStatus` / `GetText` / `GetIcon`、`ITfDisplayAttributeProvider` | 固定値・アトミック値だけ | 変更なし |

**登録・解除の記録**: `DllRegisterServer` と `DllUnregisterServer` の両方で、時刻・PID・各段階の結果を `register_debug.log` に追記する（今は登録だけ、上書き）。`unregister_server()` は各解除の結果を返すようにする。tracing には頼らない。

**`DLL_PROCESS_DETACH` でスレッドの終了を待たない**（ローダーロック下のデッドロック）。Activate 後は PIN でアンロードされないので、監視スレッドの停止経路は無いままでよい。

**既定の設定ファイルの作成の競合**: `exists()` の確認と `write()` の間に作られた設定を上書きしうる（`config.rs:823-830`、`keymap.rs:543-547`）。新規作成だけを行う形（`create_new`）にする。

### 段 2: 書き手を 1 つに限り、発生元を特定できるようにする — #73

- `.lock` を排他で取れたときだけ writer を作る。取れなければ、起動識別子を変えて上限回数まで再試行し、それでも取れなければログなしで続ける。
- ヘッダー（各ファイルの 1 行目）: 実行ファイルのフルパス、パッケージファミリー名（`GetCurrentPackageFamilyName`、無ければ無し）、PID、起動識別子、ビルド。**ローテーションで新しい本体を開くたびに書く**（今は初回の 1 回だけ）。
- 各行: PID・TID（`tracing_subscriber` で付けられる範囲）。ヘッダーにしか無い項目と、各行にある項目を分けて文書に書く。
- ファイル名は今の `<PID>-<起動識別子>` を保つ（書き手を 1 つにする目的には適切。アプリごとに番号を使い回す方式は、同じアプリの履歴を 1 ファイルに溜めたい要求があるときの選択肢として残す）。
- ログレベルの指定を文書にまとめる: TSF は `RAKUKAN_LOG` → `config.toml` の `log_level` → `debug`、engine DLL は `RAKUKAN_LOG` → `info`、ホストは `RUST_LOG` → `info`。変更が効く時期と、不正な値のときの動作も書く。

### 段 3: 掃除をトレイへ移し、消す条件を増やす — #74

**前提**: インストーラーでのトレイの配布・起動・Run 登録・解除は #33 で行う（`docs/Installer_Redesign_Plan.md` の 4.3a）。それまでは、`.iss` で入れた環境では掃除が行われない（制限）。

段 3 で行うこと:

- トレイの多重起動の抑止、掃除用のタイマー、トレイ自身のログ（同じ保持規則）。
- 掃除は UI スレッドで行わない。

**条件**（2026-10-10 決定。どちらか一方でも超えたら、古いインスタンスから消す。順序: 日数 → 件数、日数の後で数え直す）:

- 日数: **90 日**。インスタンスの最終時刻 = 本体・全退避世代・`.tmp` の最終更新日時の最大値で判定する。起動時刻では判定しない（長く動くプロセスの新しい記録を消さないため）。
- 件数: **30000 ファイル**（本体・退避世代・`.tmp`・`.lock` を含む）。
- 合計容量: **上限を設けない**（今の 256MiB の目安は廃止する）。参考: 2026-09-19〜10-10 の実測（debug）は TSF だけで 1 日平均 5.28MiB・ログ 92 個（`.lock` を含め 184 個）で、90 日分は約 475MiB・約 16600 個。
- 実行: **トレイの起動時だけ**。トレイが起動しない間は掃除されない（制限として明記）。

**規則**:

- 消す前にインスタンスの `.lock` を排他で取り、取れたものだけ消す。ログが残ったら `.lock` も残す（今と同じ）。
- ログが無く `.lock` だけ残ったインスタンス: `.lock` を排他で取れたら消す（今の列挙は `.lock` を数えないので新しく加える）。
- 旧 `rakukan.log` / `.1`〜`.5`（0.11.8 まで）: **消す**（2026-10-10 決定）。`.lock` による使用中の判定ができないので、日数の条件だけで、最終更新が 90 日を超えたものを消す。
- 対象: TSF、段 4 のホスト・DLL のインスタンスごとのログ、トレイのログ。

### 段 4: ホスト・engine DLL のログを揃える — #75

- **ホスト**: `RotatingLog`（書き込み時ローテーション）にし、名前を `rakukan-engine-host-<PID>-<起動識別子>.log` + `.lock` にする。ログの初期化は多重起動の判定より後にする。stderr は、同じパスを別ハンドルで開くのをやめ、パイプで受けて同じ writer に流す（llama.cpp などの `fprintf(stderr)` を失わないため）。
- **engine DLL**: **(b) を採る**（2026-10-10 決定。(a) は採らない）。
  - (a) DLL もインスタンスごとのファイルにする（`rakukan-engine-dll-<backend>-<ホストの PID>-<起動識別子>.log` + `.lock`）。ABI は変えない。
  - (b) DLL のログを C ABI の callback でホストへ渡し、ホストの writer に書く。callback の登録時期（最初の `engine_create` より前）、背景スレッドからの呼び出し、再入の禁止、文字列の所有権、panic の境界、解除前に全呼び出しを終えること、失敗時は捨てること、を定める。ABI の版を上げる（2 か所で定義）。
- `RotatingLog`・ヘッダー・掃除の処理は、TSF・ホスト・DLL・トレイで共有する crate に移す（名前は未決）。共有 crate にしても、EXE と DLL の subscriber は別々のまま。

### 段 5: ファイルの書き込みを別スレッドへ移し、ETW を調査用に併用する — #76

**ファイルのログを主にし、ETW は調査のときだけ使う**（2026-10-10 決定）。ETW を常時の記録にはしない（セッションの開始に管理者の権限が要り、セッションが無い間は何も残らないため）。

**ファイルの書き込みを別スレッドへ移す**（キー処理でファイル I/O を待たないため）:

- キー処理などの呼び出し元は、整形した行を上限つきのキューに入れるだけにする。サイズ確認・退避・書き込みは書き込み用のスレッドで行う。
- キューが満杯のときは待たずに捨て、捨てた行数を数えて、次に書けたときに 1 行で記録する。
- TSF では、書き込み用のスレッドは段 1 の初期化（Activate 後、DLL を PIN した後）で起動する。ホストでも同じ仕組みを使う（段 4 の共有 crate）。
- プロセスの終了時・落ちたときにキューに残った行は失われうる（制限として明記）。重要な行（エラーなど）だけ同期で書くかは、実装時に決める。

**ETW（調査用）**:

- 各コンポーネント（TSF・ホスト・engine DLL）を ETW の provider にする。セッションは、調査するときに利用者が管理者の権限で手で開始・停止する（開始・停止・テキストへの書き出しの手順と道具を用意する）。常時のセッションは作らない。
- Rust から使う手段: Microsoft の `tracelogging`（MIT、固定スキーマ）、`tracelogging_dynamic`（実行時スキーマ、tracing の Layer 向き。ライセンスは採用する版で確認）、または `windows` crate の ETW API（MIT / Apache-2.0。今の TSF の `windows` 0.58 では feature を足す必要がある）。
- セッション（循環 ETL）の開始・停止には、通常は管理者か Performance Log Users の権限が要る。手順には、既に動いているセッション・残ったセッションの扱いと、容量の指定を含める。
- provider は Activate 前の照会・登録・解除では登録しない。engine DLL の provider は、`DynEngine` が DLL を外す前に解除する。
- 入力の内容を含むイベントの既定のレベルと、集める範囲を決める。
- 欠落数をセッションの統計から取り、書き出し時にも残す。RPC をまたぐ因果を追えるように、要求・activity の ID を持たせる。

## 5. 既存のファイルの扱い（移行）

- 最初に一覧（名前・大きさ・時刻の範囲）を記録する。
- 使用中（`.lock` を排他で取れない）のものは残す。新しい名前へ一括で改名しない。
- `.tmp`（退避の途中）は内容を確かめてから扱う。
- 段 3 の掃除で、条件に従って消える。
- 旧版から更新するときの、旧版の DLL での登録解除（`/u`）の扱いは #33 で行う（`docs/Installer_Redesign_Plan.md` の 4.3a）。

## 6. 文書と道具

- `scripts/merge-logs.ps1`: ホスト・DLL・トレイのログも対象にする。PID の絞り込みを、ファイル名ではなくヘッダーで行う。同じ時刻の行の並びは因果の順を保証しないことを表示する。全行をメモリに読む今の作りが長期の保存で重くならないか測る。
- 更新する文書: `README.md`（ログの節）、`docs/DESIGN.md`（ログの節）、`docs/INVESTIGATION_GUIDE.md`、`.claude/CLAUDE.md`（ログの説明）。「本体 + 退避 5 世代」「容量の上限は無く、日数と件数で消す」「欠落の条件」「時刻はファイルの作成日時ではなく本文の UTC」を書く。

## 7. 試験

| 試験 | 見ること |
|---|---|
| x64 / x86 の regsvr32 で登録・解除を繰り返す（ログのファイルが数千ある状態を含む） | 終了コード 0。実行時のログ・`.lock`・スレッドを作らない。`register_debug.log` の各段階の結果と、レジストリの登録状態が合う |
| 任意のプロセスで `LoadLibrary` → `FreeLibrary` を繰り返す（Activate なし） | 落ちない。スレッド・ウィンドウ・ファイルを作らない |
| Activate / Deactivate の後に `FreeLibrary` | PIN により外れない |
| Activate 前の照会（ClassFactory の生成、言語バーのツールチップ・メニュー） | 設定の読み込み・スレッド・ホストの起動をしない |
| 複数の STA、Activate / Deactivate の繰り返し | 初期化が 1 回、writer と監視が重複しない。再入で止まらない |
| 初期化と設定の保存の競合 | Activate 前・監視開始の境目・読み込み中の保存・既定ファイルの作成と同時の保存を逃さない |
| Activate の所要時間 | 初回と、同時の Activate の待ち時間 |
| ログの初期化・監視の起動の失敗 | 入力が止まらない |
| 掃除の条件 | 日数・件数の各境界、使用中のログを消さない、長く動くプロセスの新しい記録を消さない、`.lock` だけのインスタンス |
| 退避の途中でプロセスを強制終了 → 再起動 | `.tmp` と既存の世代を失わない |
| ディスク満杯・アクセス拒否・共有違反 | 入力を止めない |
| 普段の利用 | 入力・変換・設定の反映（#65）・ホストの再接続 |
